# 仓库整理约定

## 目标结构

每道题以独立目录保存，目录中优先使用以下命名：

```text
比赛/方向/题目名/
├── README.md        # 原始题面、writeup、复现与来源
├── attachment/      # 官方附件，尽量保持原始文件名
├── src/             # 解包后的题目源码（若有）
├── solve.py         # 可重复运行的最终解答
└── notes/           # IDA 数据库、截图和探索性草稿
```

当前仓库来自单次历史快照，直接搬移会让大量脚本的相对路径失效。因此第一轮采用“先文档化、后迁移”：保留所有原文件位置，为可识别的题目增加 README，并在后续逐题复现时再迁移。

## 状态定义

- **已有完整 writeup**：推导、最终脚本和结果都已记录。
- **solve 可用**：存在看起来完整的求解脚本，但仍需环境复现。
- **解题草稿**：有分析或脚本，可能依赖失效远端、硬编码地址或缺少结论。
- **待补 solve/writeup**：题目附件基本存在，但没有可靠解答。
- **材料不完整**：缺少题面输出、附件或其他求解所需信息。

“脚本能运行”与“题目已复现”不是一回事。只有在隔离环境中从原始附件出发得到预期结果，状态才能改为“已复现”。

## 文件保留原则

1. 官方附件尽量原样保留，并补 SHA-256。
2. 历史实验脚本不覆盖；稳定解答另存为 `solve.py`。
3. 不提交真实 flag、`.env`、服务密钥和新生成的缓存/编译产物。
4. 第三方源码应注明项目、版本与许可证；后续可改为下载说明，避免仓库膨胀。
5. 外部 writeup 只记录链接和自己的总结，不整篇复制。

## 安全复现

仓库包含来源不一的 ELF、PE、脚本与容器。不要直接在宿主机运行未知二进制；优先使用无网络、低权限、一次性的容器或虚拟机。历史脚本中的远程地址只作为记录，不应默认连接。
