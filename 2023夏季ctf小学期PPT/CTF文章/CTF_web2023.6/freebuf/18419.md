Adobe Acrobat Reader DC堆缓冲区溢出漏洞分析
2021-10-18 17:35:14

6 月下旬，我们发布了一篇博客文章，分析了 Adob​​e Reader 中堆缓冲区溢出漏洞的利用情况，我们认为该漏洞对应于 CVE-2021-21017。该研究的起点是根本原因分析 POC。博文发布后不久，我们了解到 CVE 不具有权威性，POC 是零日漏洞。我们立即从博客中取出帖子并开始调查。

进一步的研究表明，该漏洞在最新版本中仍然存在，只有对我们的漏洞进行一些修改才能被利用。我们向 Adob​​e 报告了我们的发现。Adobe 已为此漏洞分配了 CVE-2021-39863 ( https://helpx.adobe.com/security/products/acrobat/apsb21-55.html)并于 2021 年 9 月 14 日发布了其产品的建议和修订版本。

由于漏洞利用非常相似，这篇文章与之前删除的博客文章有很多重叠。它在 Adob​​e Acrobat Reader DC 中解析并使用 CVE-2021-39863 ( https://nvd.nist.gov/vuln/detail/CVE-2021-39863)堆缓冲区溢出，直到并包括版本 2021.005.20060。

这篇文章 ( https://blog.exodusintel.com/2021/0...ree-vulnerability-in-adobe-acrobat-reader-dc/)类似于我们之前关于 Adob​​e Acrobat Reader 的文章，它利用了 UAF 漏洞处理 Unicode 和 ANSI 字符串时也会发生这种情况。

概述

当您连接与 PDF 文档的基本 URL 匹配的 ANSI 字符串时，会发生堆缓冲区溢出。当内联 JavaScript 调用位于处理 Internet 访问的 IA32.api 模块中的函数（例如 this.submitForm 和 app.launchURL）时，就会发生这种情况。当使用编码与 PDF 文件基本 URL 编码不同的相对 URL 调用这些函数时，相对 URL 被视为与 PDF 文件的路径具有相同的编码。这可能导致 ANSI 源字符串（相对 URL）的两倍字节被复制到适当大小的目标缓冲区中，从而导致越界读取和堆缓冲区溢出。

CVE-2021-39863

Acrobat Reader 具有基于 Mozilla SpiderMonkey 的内置 JavaScript 引擎。PDF 文件中的嵌入式 JavaScript 由Adobe Reader 中的 EScript.api 模块 ( http://web.archive.org/web/20201124...m/en/devnet/acrobat/pdfs/js_api_reference.pdf)处理和执行。

Internet 访问操作由 IA32.api 模块处理。当通过组合 PDF 文档的基本 URL 和相对 URL 生成 URL 时，此模块中会出现此漏洞。在调用触发任何类型的 Internet 访问的 JavaScript 函数（例如 this.submitForm 和 app.launchURL）时，此相对 URL 被指定为参数。特别是当两个字符串的编码不同时，就会出现该漏洞。

两行的连接是通过分配足够的内存来容纳最后一行来完成的。无论是ANSI还是Unicode，这两个字符串的长度计算都是正确的。但是，当发生连接时，只检查基本 url 编码，并且相对 url 被认为与基本 url 具有相同的编码。当相对 URL 是 ANSI 编码时，将字节从相对 URL 字符串缓冲区复制到分配的缓冲区的代码一次复制两个字节，而不是一次一个字节。这会导致从源缓冲区外部读取与相对 URL 长度相等的字节数并复制到相同长度的目标缓冲区之外，从而导致超出范围的读取和超出范围的写入.

利用

我们现在看看如何利用此漏洞来执行任意代码。

为了开发该漏洞，我们在 Windows 10 x64 下使用了 Adob​​e Acrobat Reader DC 版本 2021.005.20048。请注意 Adob​​e Acrobat Reader DC 是一个 32 位应用程序。成功的利用策略必须绕过以下安全措施：

- 地址空间随机化 (ASLR)

- 数据执行预防 (DEP)

- 控制流保护 (CFG) 该

利用不会绕过以下保护机制：

- 控制流保护 ( CFG)：必须在 Windows 机器上禁用 CFG 才能使用此漏洞。这可以在 Windows 10 的漏洞利用保护设置中通过默认将控制流保护 (CFG) 设置为关闭来完成。

为了利用该漏洞绕过ASLR和DEP，采用以下策略：

1. 准备堆布局，以便您可以控制与为基本URL和相对URL所做的分配相邻的内存区域。这包括进行足够的分配以激活两种大小的低堆碎片存储桶，以及进行足够的分配以完全适合 UserBlock。与基本 url 分配大小相同的选择必须包含一个 ArrayBuffer 对象，而与相对 url 大小相同的分配必须具有用值 0xffff 覆盖这些 ArrayBuffer 对象之一的 byteLength 字段所需的数据。

准备堆布局

可以控制与此漏洞相关的行的大小。这很方便，因为它允许您为每个选择正确的大小，以便它们由低碎片堆处理 ( https://web.archive.org/web/20210419095256/http://www.illmatics.com/理解_the_LFH.pdf)... 可以利用低碎片堆 (LFH) 的内部工作原理来增加利用此漏洞所需的内存结构的确定性。选择程序中未使用的大小可以让您完全控制相应 LFH 段的激活，并执行容纳一个 UserBlock 所需的确切数量的选择。

当进行分配时，UserBlock 中的内存块会随机返回给用户。利用此漏洞所需的理想布局是将空闲块与受控块相邻，因此当分配触发漏洞所需的行时，它们最终会位于这些空闲块之一中。

为了创建这样的布局，需要分配 0xd + 0x11 个大小为 0x2608-0x10-0x8 的 ArrayBuffers。第一个0x11分配用于启用LFH桶，接下来的0xd分配用于填充UserBlock（注意这个桶大小的第一个UserBlock中的碎片数量并不总是0xd，所以这种方法不是100%高效的）。ArrayBuffer 的大小使得底层分配为 0x2608（包括块元数据），这对应于应用程序未使用的 LFH 存储桶。
