Log4j又爆命令执行漏洞？Log4j2.17.0 RCE(CVE-2021-44832)分析
2021-12-29 14:47:44

前言

最近关于log4j2的漏洞热度很高，当大家还沉浸在CVE-2021-44228带来的激动之中时，昨天晚上突然之间爆出Log4j2.17.0存在RCE漏洞。最初以为这也是一个高危的漏洞，会是原来CVE-2021-44228的某种绕过，但后面发现并不是，和之前差距很大。

首先回答大家关心的一个问题，这个漏洞是不是高危漏洞，影响力怎么样？答案是这并不是一个高危漏洞，官方还没给出CVSS的具体评分，预计应该在6.6左右，勉强算一个中危漏洞，利用条件比较苛刻，实际影响较小。


漏洞复现

这个漏洞要实际利用成功，需要用户攻击者可控log4j2的配置文件log4j2.xml文件。要达到这个效果可以有两种应用场景。

1）当log4j2采用远程配置文件加载时，可以结合中间人攻击，篡改返回的配置文件内容。

2）当有目标机器权限时，可以通过直接修改log4j2配置文件，留下一个隐蔽的log4j2后门。

本地采用mvn下载log4j2.17.0的jar包，相关配置如下。

修改log4j2.xml配置文件，采用databaseAppender模式，并加载远程的JNDI对象。

在远程服务器上开启ldap服务（这一步省略，之前已经说过了）。然后本地运行一个基础的日志记录功能就能触发RCE效果。

漏洞原理

这个漏洞产生的根本原因有点类似于之前已经爆出的关于log4j1的RCE，都是通过配置文件修改达到远程命令执行的效果。

采用databaseAppender模式记录日志的过程中，在解析配置文件时，DataSourceConnectionSource类中会调用JNDI操作，并且传输的参数来源于配置文件，如下图所示，这就造成了JNDI注入的可能：

修复建议

建议用户及时升级到 Log4j 2.3.2（适用于 Java 6）、2.12.4（适用于Java 7）或 2.17.1（适用于 Java 8 及更高版本）

官方下载地址：

https://logging.apache.org/log4j/2.x/download.html


注：从2.17.1版本（适用于 Java 8 及更高版本）、2.12.4（适用于Java 7）、2.3.2（适用于 Java 6）开始，已删除对 LDAP 协议的支持，并且 JNDI 连接仅支持 JAVA 协议。启用 JNDI 的属性已从“log4j2.enableJndi”重命名为三个单独的属性：log4j2.enableJndiLookup、log4j2.enableJndiJms 和 log4j2.enableJndiContextSelector。
