在您开始寻找错误之前，让我们花点时间了解互联网的工作原理。寻找网络漏洞就是利用这项技术的弱点，所以所有优秀的黑客都应该对它有深入的了解。如果您已经熟悉这些流程，请随时跳到我对互联网安全控制的讨论。

以下问题提供了一个很好的起点：当您在浏览器中输入 www.google.com 时会发生什么？换句话说，您的浏览器如何知道如何从域名（例如 google.com）转到您要查找的网页？让我们来了解一下。

客户端-服务器模型

互联网由两种设备组成：客户端和服务器。客户端请求资源或服务，服务器提供这些资源和服务。当您使用浏览器访问网站时，它充当客户端并向 Web 服务器请求网页。然后 Web 服务器将向您的浏览器发送网页。

网页只不过是 Web 服务器发送的资源或文件的集合。例如，服务器至少会向您的浏览器发送一个用超文本标记语言 (HTML) 编写的文本文件，该语言告诉您的浏览器要显示什么。大多数网页还包含级联样式表 (CSS) 文件以使其美观。有时网页还包含 JavaScript (JS) 文件，这些文件使网站能够为网页设置动画并对用户输入做出反应，而无需通过服务器。例如，JavaScript 可以在用户滚动页面时调整图像大小，并在将用户输入发送到服务器之前在客户端验证用户输入。最后，您的浏览器可能会收到嵌入的资源，例如图像和视频。您的浏览器将组合这些资源以显示您看到的网页。

服务器也不只是将网页返回给用户。 Web API 使应用程序能够请求其他系统的数据。这使应用程序能够相互交互并以受控方式共享数据和资源。例如，Twitter的 API 允许其他网站向 Twitter 的服务器发送请求，以检索公共推文及其作者列表等数据。 API 支持许多除此之外的 Internet 功能，我们将在后面重新讨论它们及其安全问题。

域名系统

您的浏览器和其他 Web 客户端如何知道在哪里可以找到这些资源？好吧，连接到 Internet 的每个设备都有一个唯一的 Internet 协议 (IP) 地址，其他设备可以使用它来查找它。但是，IP 地址由人类难以记住的数字和字母组成。例如，旧格式的 IP 地址 IPv4 如下所示：123.45.67.89。新版本 IPv6 看起来更加复杂：2001:db8::ff00:42:8329。

这就是域名系统 (DNS) 的用武之地。DNS 服务器充当 Internet 的电话簿，将域名转换为 IP 地址（图 3-2）。当您在浏览器中输入域名时，DNS 服务器必须首先将域名转换为 IP 地址。我们的浏览器询问 DNS 服务器，“这个域位于哪个 IP 地址？”

互联网端口

在您的浏览器获取正确的 IP 地址后，它将尝试通过端口连接到该 IP 地址。端口是设备上标识特定网络服务的逻辑分区。我们通过端口号来识别端口，端口号的范围可以从 0 到 65,535。

默认情况下，我们对 HTTP 消息使用端口 80，对 HTTPS（HTTP 的加密版本）使用端口 443。

HTTP 请求和响应

建立连接后，浏览器和服务器将通过超文本传输协议 (HTTP) 进行通信。HTTP 是一组规则，用于指定如何构建和解释 Internet 消息，以及 Web 客户端和 Web 服务器应如何交换信息。

当您的浏览器想要与服务器交互时，它会向服务器发送 HTTP 请求。HTTP 请求有多种类型，最常见的两种是 GET 和 POST。按照惯例，GET 请求从服务器检索数据，而 POST 请求向服务器提交数据。其他常见的 HTTP 方法包括 OPTIONS，用于为给定的 URL 请求允许的 HTTP 方法；PUT，用于更新资源；和 DELETE，用于删除资源。

下面是一个请求服务器提供 www.google.com 主页的示例 GET 请求：

GET / HTTP/1.1 
Host: www.google.com 
User-Agent: Mozilla/5.0 
Accept: text/html,application/xhtml+xml,application/xml 
Accept-Language: en-US 
Accept-Encoding: gzip, deflate 
Connection: close


请求行是 HTTP 请求的第一行。它指定请求方法、请求的 URL 和使用的 HTTP 版本。在这里，您可以看到客户端正在使用 HTTP 1.1 版向 www.google.com 的主页发送 HTTP GET 请求。

其余行是 HTTP 请求标头。这些用于将有关请求的附加信息传递给服务器。这允许服务器自定义发送到客户端的结果。在前面的示例中，Host 标头指定请求的主机名。User-Agent 标头包含请求软件的操作系统和软件版本，例如用户的 Web 浏览器。Accept、Accept-Language 和 Accept-Encoding 标头告诉服务器响应应该采用哪种格式。 Connection 标头告诉服务器在服务器响应后网络连接是否应该保持打开状态。

您可能会在请求中看到其他一些常见的标头。Cookie 标头用于将 cookie 从客户端发送到服务器。Referer 标头指定链接到当前页面的前一个网页的地址。并且 Authorization 标头包含向服务器验证用户身份的凭据。

服务器收到请求后，将尝试完成它。服务器将使用 HTTP 响应返回用于构建您的网页的所有资源。一个 HTTP 响应包含多个内容：一个 HTTP 状态代码，用于指示请求是否成功；HTTP 标头，这是浏览器和服务器用来相互通信的有关身份验证、内容格式和安全策略的一些信息；和 HTTP 响应正文，或您请求的实际 Web 内容。Web 内容可能包括 HTML 代码、CSS 样式表、JavaScript 代码、图像等。

以下是 HTTP 响应的示例：

HTTP/1.1 200 OK 
Date: Tue, 31 Aug 2021 17:38:14 GMT 
[...] 
Content-Type: text/html; charset=UTF-8 
Server: gws 
Content-Length: 190532 
<!doctype html> 
[...] 
<title>Google</title> 
[...] 
<html>


请注意第一行 1 上的 200 OK 消息。这是状态代码。 200 范围内的 HTTP 状态代码表示请求成功。 300 范围内的状态代码表示重定向到另一个页面，而 400 范围表示客户端的错误，例如请求不存在的页面。 500 范围意味着服务器本身遇到了错误。 作为漏洞赏金猎人，您应该始终关注这些状态代码，因为它们可以告诉您很多关于服务器如何运行的信息。例如，状态码 403 表示禁止您使用该资源。 这可能意味着敏感数据隐藏在您可以绕过访问控制可以访问的页面上。 响应中由冒号 (:) 分隔的接下来几行是 HTTP 响应标头。它们允许服务器将有关响应的附加信息传递给客户端。在这种情况下，您可以看到响应的时间是 2021 年 8 月 31 日星期二 17:38:14 GMT 2。 Content-Type 标头指示响应正文的文件类型。在这种情况下，此页面的 Content-Type 为 text/html 3. 服务器版本为 Google Web Server (gws) 4，Content-Length 为 190,532 字节 5. 通常，额外的响应头会指定内容的格式，语言和安全策略。 除了这些之外，您可能还会遇到一些其他常见的响应头。 Set-Cookie 头由服务器发送到客户端以设置 cookie。 Location 标头指示要将页面重定向到的 URL。

Access-Control-Allow-Origin 标头指示哪些来源可以访问页面的内容。
Content-Security-Policy 控制允许浏览器加载的资源的来源，而 X-Frame-Options 标头指示页面是否可以在 iframe 中加载。
空行后的数据是响应正文。它包含网页的实际内容，例如 HTML 和 JavaScript 代码。一旦您的浏览器接收到构建网页所需的所有信息，它就会为您呈现所有内容。

互联网安全控制

既然您对信息如何通过 Internet 进行通信有了高层次的了解，让我们深入了解一些保护信息免受攻击者侵害的基本安全控制措施。为了有效地寻找错误，您通常需要想出创造性的方法来绕过这些控件，因此您首先需要了解它们的工作原理。

内容编码

在 HTTP 请求和响应中传输的数据并不总是以纯旧文本的形式传输。网站通常以不同的方式对其消息进行编码，以防止数据损坏。

数据编码被用作一种在对不同内容类型支持有限的机器之间可靠地传输二进制数据的方法。用于编码的字符是在 Internet 协议中不用作受控字符的常用字符。因此，当您使用通用编码方案对内容进行编码时，您可以确信您的数据将完好无损地到达目的地。相比之下，当您以原始状态传输数据时，当互联网协议误解消息中的特殊字符时，数据可能会被搞砸。

Base64 编码是最常见的数据编码方式之一。它通常用于在网络消息中传输图像和加密信息。这是字符串“内容编码”的 base64 编码版本：
Q29udGVudCBFbmNvZGluZw==

Base64 编码的字符集包括大写字母字符 A 到 Z、小写字母字符 a 到 z、数字字符 0 到 9、字符 + 和 /，最后是用于填充的 = 字符。Base64url 编码是用于 URL 格式的 base64 的修改版本。它类似于 base64，但使用不同的非字母数字字符并省略填充。

另一种流行的编码方法是十六进制编码。十六进制编码或十六进制是一种以 base-16 格式表示字符的方式，其中字符的范围从 0 到 F。十六进制编码占用更多空间，效率比 base64 低，但提供了更易读的编码字符串。这是字符串“内容编码”的十六进制编码版本；你可以看到它比它的 base64 对应物占用更多的字符：
436f6e74656e7420456e636f64696e67

URL 编码是一种将字符转换为更易于通过 Internet 传输的格式的方法。 URL 编码字符串中的每个字符都可以由其指定的十六进制数字表示，前面有一个 % 符号。有关 URL 编码的更多信息，请参阅维基：https://en.维基.org/wiki/Percent-encoding。 例如，单词 localhost 可以用它的 URL 编码等价物来表示，%6c%6f%63%61%6c%68%6f%73%74。您可以使用 URL 解码器和编码 (https://www.urlencoder.org/) 等
URL 计算器来计算主机名的 URL 编码等效项。

当我们在讨论 SSRF 时，我们将介绍几种额外的字符编码类型——八进制编码和双字编码。 当你在调查网站时看到编码内容时，总是尝试对其进行解码以发现网站正在尝试的内容交流。您可以使用 Burp Suite 的解码器来解码编码内容。我们将在下一章介绍如何做到这一点。或者，您可以使用 CyberChef (https://gchq.github.io/CyberChef/) 来解码 base64 内容和其他类型的编码内容。

服务器有时也会在传输前对其内容进行加密。这使客户端和服务器之间的数据保持私密，并防止任何拦截流量的人窃听消息。

会话管理和 HTTP Cookie

为什么每次关闭电子邮件选项卡时都不必重新登录？这是因为网站会记住您的会话。会话管理是一个过程，它允许服务器处理来自同一用户的多个请求，而无需要求用户再次登录。

网站为每个登录的用户维护一个会话，当您登录网站时，一个新的会话开始。服务器将为您的浏览器分配一个关联的会话 ID，作为您身份的证明。会话 ID 通常是一个很长且不可预测的序列，设计为不可猜测。当您注销时，服务器会结束会话并撤销会话 ID。如果您不手动注销，该网站也可能会定期结束会话。

大多数网站使用 cookie 在 HTTP 请求中传达会话信息。HTTP cookie 是网络服务器发送到您的浏览器的小块数据。当您登录站点时，服务器会为您创建一个会话，并将会话 ID 作为 cookie 发送到您的浏览器。收到 cookie 后，您的浏览器会存储它并将其包含在对同一服务器的每个请求中。

这样服务器就知道是你了！会话的 cookie 生成后，服务器将跟踪它并使用它来验证您的身份。最后，当您注销时，服务器将使会话 cookie 失效，使其无法再次使用。下次登录时，服务器将为您创建一个新会话和一个新的关联会话 cookie。

基于令牌的认证

在基于会话的身份验证中，服务器存储您的信息并使用相应的会话 ID 来验证您的身份，而基于令牌的身份验证系统将此信息直接存储在某种令牌中。令牌不是在服务器端存储您的信息并使用会话 ID 查询它，而是允许服务器通过对令牌本身进行解码来推断您的身份。这样，应用程序就不必在服务器端存储和维护会话信息。

这个系统存在一个风险：如果服务器使用令牌中包含的信息来确定用户的身份，用户不能修改令牌中的信息并以其他人的身份登录吗？为防止此类令牌伪造攻击，一些应用程序对其令牌进行加密，或对令牌进行编码，使其只能由应用程序本身或其他授权方读取。如果用户无法理解令牌的内容，他们也可能无法有效地篡改它。加密或编码令牌并不能完全防止令牌伪造。攻击者可以通过多种方式在不了解其内容的情况下篡改加密令牌。但这比篡改明文令牌要困难得多。攻击者通常可以解码编码的令牌以篡改它们。

应用程序保护令牌完整性的另一种更可靠的方法是签署令牌并在令牌到达服务器时验证令牌签名。签名用于验证一段数据的完整性。它们是特殊的字符串，只有在您知道密钥时才能生成。由于没有密钥就无法生成有效签名，并且只有服务器知道密钥是什么，因此有效签名表明令牌可能没有被客户端或任何第三方更改。尽管应用程序的实现可能会有所不同，但基于令牌的身份验证的工作方式如下：

用户使用其凭据登录。

服务器验证这些凭据并向用户提供签名令牌。

用户在每次请求时都发送令牌以证明其身份。

服务器收到并验证令牌后，从令牌中读取用户的身份信息，并以机密数据进行响应。

JSON Web Tokens

JSON Web Token (JWT) 是最常用的身份验证令牌类型之一。它具有三个组成部分：标头、有效载荷和签名。
关于JWT振奋人心的测试实施可以参考：https://www.freebuf.com/articles/web/289650.html

每个靶机教学都是作者呕心沥血测试实施的心血，不可小觑，当效仿与传承。

标头标识用于生成签名的算法。它是一个包含算法名称的 base64url 编码字符串。JWT 标头如下所示：
eyBhbGcgOiBIUzI1NiwgdHlwIDogSldUIH0K
此字符串是此文本的 base64url 编码版本：
{ "alg" : "HS256", "typ" : "JWT" }

有效载荷部分包含有关用户身份的信息。此部分也在用于令牌之前进行了 base64url 编码。这是有效负载部分的示例，它是 { "user_name" : "admin", } 的 base64url 编码字符串：
eyB1c2VyX25hbWUgOiBhZG1pbiB9Cg

最后，签名部分验证用户没有篡改令牌。它的计算方法是将标头与有效负载连接起来，然后使用标头中指定的算法和密钥对其进行签名。JWT 签名如下所示：
4Hb/6ibbViPOzq9SJflsNGPWSk6B8F6EqVrkNjpXh7M
对于这个特定的令牌，签名是通过签署字符串 eyBhbGcgOiBIUzI1NiwgdHlwIDogSldUIH0K.eyB1c2VyX25hbWUgOiBhZG1pbiB9Cg 使用 HS256 算法使用密钥。完整的令牌将每个部分（标头、有效负载和签名）连接起来，并用句点 (.) 分隔它们：
eyBhbGcgOiBIUzI1NiwgdHlwIDogSldUIH0K.eyB1c2VyX25hbWUgOiBhZG1pbiB9Cg.4Hb/6ibbVi
POzq9SJflsNGPWSk6B8F6EqVrkNjpXh7M

正确实施后，JSON Web 令牌提供了一种安全的方式来识别用户。当令牌到达服务器时，服务器可以通过检查签名是否正确来验证令牌未被篡改。然后服务器可以通过使用负载部分中包含的信息来推断用户的身份。由于用户无权访问用于签署令牌的密钥，因此他们无法更改有效负载并自行签署令牌。

但如果实施不当，攻击者可以通过多种方式绕过安全机制并伪造任意令牌。

操作 alg 字段

有时，应用程序在令牌到达服务器后无法验证令牌的签名。这允许攻击者通过提供无效或空白签名来简单地绕过安全机制。

攻击者伪造自己的令牌的一种方法是篡改令牌标头的 alg 字段，该字段列出了用于对签名进行编码的算法。如果应用程序不限制 JWT 中使用的算法类型，攻击者可以指定使用哪种算法，这可能会危及令牌的安全性。

JWT 支持算法类型的 none 选项。如果 alg 字段设置为 none，则即使签名部分为空的令牌也将被视为有效。例如，考虑以下令牌：
eyAiYWxnIiA6ICJOb25lIiwgInR5cCIgOiAiSldUIiB9Cg.eyB1c2VyX25hbWUgOiBhZG1pbiB9Cg.
这个令牌只是这两个 blob 的 base64url 编码版本，没有签名：
{ "alg" : "none", "typ" : "JWT" } { "user" : "admin" }

此功能最初用于调试目的，但如果在生产环境中不关闭，它将允许攻击者伪造他们想要的任何令牌并冒充站点上的任何人。

攻击者可以利用 alg 字段的另一种方法是更改使用的算法类型。用于 JWT 的两种最常见的签名算法类型是 HMAC 和 RSA。HMAC 要求使用密钥对令牌进行签名，然后使用相同的密钥进行验证。使用 RSA 时，令牌将首先使用私钥创建，然后使用任何人都可以读取的相应公钥进行验证。HMAC 令牌的密钥和 RSA 令牌的私钥必须保密，这一点至关重要。

现在假设应用程序最初设计为使用 RSA 令牌。令牌使用私钥 A 签名，该私钥对公众保密。然后使用公钥 B 验证令牌，任何人都可以使用该公钥。只要令牌始终被视为 RSA 令牌，这就可以了。现在，如果攻击者将 alg 字段更改为 HMAC，他们可能能够通过使用 RSA 公钥 B 对伪造的令牌进行签名来创建有效的令牌。密钥 B，但这一次，令牌也可以使用相同的公钥进行签名。

Brute-Forcing the Key

也可以猜测或暴力破解用于签署 JWT 的密钥。攻击者可以从很多信息入手：用于对令牌进行签名的算法、已签名的有效负载以及由此产生的签名。如果用于对令牌进行签名的密钥不够复杂，他们可能能够轻松地对其进行暴力破解。如果攻击者无法暴力破解密钥，他们可能会尝试泄露密钥。如果存在另一个漏洞，例如目录遍历、外部实体攻击 (XXE) 或 SSRF，允许攻击者读取存储密钥值的文件，则攻击者可以窃取密钥并签署他们选择的任意令牌。我们将在后面的讨论这些漏洞。

阅读敏感信息

由于 JSON Web 令牌用于访问控制，因此它们通常包含有关用户的信息。如果令牌未加密，任何人都可以对令牌进行 base64 解码并读取令牌的有效负载。如果令牌包含敏感信息，它可能会成为信息泄漏的来源。JSON Web 令牌的正确实施的签名部分提供数据完整性，而不是机密性。这些只是 JWT 安全问题的几个例子。有关 JWT 漏洞的更多示例，请使用搜索词 JWT 安全问题。任何身份验证机制的安全性不仅取决于其设计，还取决于其实现。JWT 可以是安全的，但前提是正确实施。

同源政策

同源策略 (SOP) 是一种规则，用于限制来自一个源的脚本如何与不同源的资源交互。一句话，SOP 是这样的：来自页面 A 的脚本可以访问来自页面 B 的数据，前提是这些页面来自同一来源。此规则可保护现代 Web 应用程序并防止许多常见的 Web 漏洞。如果两个 URL 共享相同的协议、主机名和端口号，则称它们具有相同的来源。让我们看一些例子。页面 A 位于此 URL：
https://medium.com/@vickieli

它使用 HTTPS，请记住，默认情况下使用端口 443。现在查看以下页面，根据 SOP 确定哪些页面与页面 A 具有相同的来源：
https://medium.com/
http://medium.com/
https://twitter.com/@vickieli7
https://medium.com:8080/@vickieli
https://medium.com/ URL 与页面 A 同源，因为这两个页面共享相同的源、协议、主机名和端口号。其他三个页面与页面 A 的来源不同。 http://medium.com/ 与页面 A 的来源不同，因为它们的协议不同。https://medium.com/ 使用 HTTPS，而 http://medium.com/ 使用 HTTP。https://twitter.com/@vickieli7 也有不同的来源，因为它有不同的主机名。最后，https://medium.com:8080/@vickieli 的来源不同，因为它使用端口 8080，而不是端口 443。

现在让我们考虑一个例子，看看 SOP 如何保护我们。假设您已登录到您的银行网站 onlinebank.com。不幸的是，您在同一个浏览器中单击了一个恶意站点attacker.com。 恶意站点向 onlinebank.com 发出 GET 请求以检索您的个人信
息。由于您已登录银行，您的浏览器会自动在您发送到 onlinebank.com 的每个请求中包含您的 cookie，即使该请求是由恶意站点上的脚本生成的。由于请求包含有效的会话 ID， onlinebank.com 的服务器通过发送包含您的信息的 HTML 页面来满足请求。 然后，恶意脚本读取并检索页面上包含的私人电子邮件地址、家庭地址和银行信息。 幸运的是，SOP 将阻止attacker.com 上托管的恶意脚本读取从onlinebank.com 返回的HTML 数据。这可以防止页面 A 上的恶意脚本获取页面 B 中嵌入的敏感信息。

但是，目前不安全的CORS漏洞可以配合此问题。 * 星号配置无法读取到以上私人信息。如果攻击者能够控制标头篡改 * 星号的域名值为attacker.com，则相当于添加了白名单。此域可以获取私人信息并返回HTML数据。* 星号虽然无法读取私人信息回来，但它可是表示着允许任何域名的白名单，又将配合其他漏洞。
