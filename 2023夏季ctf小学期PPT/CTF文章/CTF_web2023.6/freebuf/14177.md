攻击者利用Web安全中的根本性缺陷窃取了价值200万美元的加密货币
2022-03-17 12:36:08

说明

本文翻译自https://freedom-to-tinker.com/2022/03/09/attackers-exploit-fundamental-flaw-in-the-webs-security-to-steal-2-million-in-cryptocurrency

作者 Henry Birge-Lee, Liang Wang, Grace Cimaszewski, Jennifer Rexfor

概述

2022 年 2 月 3 日星期四，攻击者从韩国加密货币交易所 KLAYswap 的用户手中窃取了价值约 200 万美元的加密货币。 安全公司 S2W 在一篇韩语博客文章中详细介绍了这次盗窃，它利用了互联网路由生态系统和公钥基础设施 (PKI) 中的系统性漏洞，使互联网上最敏感的金融和医疗行业的网站也容易受到攻击。

值得注意的是，早在几年前，普林斯顿大学的研究人员就预测到了在野的此类攻击，并成功开发了针对它的初步对策（下文将介绍）。 但除非这些缺陷得到整体解决，否则大量应用程序可能会受到完全相同类型攻击的危害。

与许多由0day漏洞（通常会迅速修补）或公然无视安全预防措施引起的攻击不同，对KLAYswap 攻击与 KLAYswap 使用的任何软件或安全配置无关。 相反，这是一个精心设计的跨层攻击示例，利用了路由系统、公钥基础设施和 Web 开发实践中的弱点。 我们将在后续的文章中更多地讨论防御措施，但防范这种攻击需要在 Web 生态系统的各个层面进行安全改进。

本次攻击中利用的漏洞尚未得到缓解。 在今天发起同样的攻击同样可行，这是因为黑客利用了 PKI 对互联网路由基础设施的信任中存在的结构性漏洞。

正文

2月3日的攻击正好发生在格林尼治标准时间凌晨1:04:18（韩国时间上午10:04），当时攻击者利用网络架构各层信任中的一个根本性漏洞入侵了KLAYswap。

KLAYswap 是一个在线加密货币交易所，为用户提供一个用于交易加密货币的Web界面。 作为其平台的一部分，KLAYswap 依赖于由韩国科技公司 Kakao Corp 编写的 JavaScript 库。当用户在加密货币交易所时，他们的浏览器将直接从 Kakao 的服务器加载 Kakao 的 JavaScript 库，网址如下（见图）：

https://developers.kakao.com/sdk/js/kakao.min.js

攻击者的目标实际上是这个 URL，而不是 KLAYswap 本身运营的任何资源。 攻击者利用一种称为边界网关协议 (BGP) 劫持的技术发起此攻击。当恶意网络上向邻近网络谎报其可以访问的 Internet 地址（或 IP 地址）时，就会发生 BGP 劫持。 如果相邻网络相信这个谎言，他们会将受害者的流量导向恶意网络，而不是连接到这些 IP 地址的合法所有者的网络，劫持因此发生。

具体来说，上面 URL 中的域名：developers.kakao.com 被解析为两个 IP 地址：121.53.104.157 和 211.249.221.246。 去往这些 IP 地址的数据包应该被路由到 Kakao公司。在攻击过程中，攻击者的恶意网络发布了两个 IP 前缀（即，路由流量时使用的 IP 地址块），导致流向这些地址的流量被导向攻击者。

当 KLAYswap 用户向攻击者请求 kakao.min.js 时，攻击者向他们提供了一个恶意 javascript 文件，导致用户的加密货币交易将资金转移到攻击者而不是预期目的地。 在进行了几个小时的攻击后，攻击者撤回了路线并通过将其代币转换为无法追踪的货币来兑现。当尘埃落定时，对手已经从 KLAYswap 的用户那里窃取了价值约 200 万美元的各种货币，并带走了价值约 100 万美元的各种加密货币。 （其中一些损失是由于从 KLAYswap 系统中提取货币相关的费用和汇率。）

但数据不是加密传输的吗？

攻击的第二个也是最危险的因素是它破坏了互联网的加密防御。 虽然与 BGP 劫持相关的攻击较复杂，但它们确实经常发生。这次攻击中前所未有的（据我们所知）是完全绕过了 TLS 协议提供的加密保护。 TLS 是万维网加密的主力军，也是网络受到越来越多安全应用程序（如金融服务和医疗系统）信任的部分原因。在其他安全属性中，TLS 旨在保护用户数据的机密性和完整性。TLS 允许 Web 服务和客户端（如 KLAYswap 的用户）甚至通过潜在的不受信任的网络（如攻击者的网络）安全地交换数据，并确保（理论上）他们正在与合法的端点交互。

然而，具有讽刺意味的是，KLAYswap 和 Kakao 正确地使用了 TLS，在攻击期间被利用的并不是 TLS 协议中的漏洞。相反，攻击利用了 TLS 在路由基础设施中放置的虚假信任。TLS 依靠公钥基础设施 (PKI) 来确认 Web 服务器的身份。 PKI 的任务是分发数字签名证书，以验证服务器的身份（在本例中是像 developers.kakao.com 这样的域名）和服务器的加密密钥。 如果服务器提供有效的证书，即使中间有另一个网络，客户端也可以加密只有真实服务器才能读取的数据。

利用其 BGP 劫持，攻击者首先针对 PKI 并对证书分发过程发起了中间人攻击。 只有在获得目标域的有效数字证书后，它才会通过加密连接提供恶意 javascript 文件，从而将攻击目标对准真实用户。

证书颁发机构（或 CA，在 PKI 中签署数字证书的机构）具有与 TLS 连接中类似的身份问题。 客户向 CA 提出签署证书的请求。 CA 需要确保请求证书的客户实际控制关联的域名。 为了验证身份（从而引导整个 TLS 生态系统的信任），CA 执行域控制验证，要求用户证明对其证书请求中列出的域的控制。 由于服务器可能是第一次获得 TLS 证书，因此域控制验证通常通过不附加安全性的 HTTP协议执行。

但现在我们回到第一个问题：攻击者只需执行 BGP 劫持以吸引来自 CA 的域控制验证流量，假装是受害者网站，并提供 CA 请求的内容。 在收到受害者域的签名证书后，攻击者可以通过所谓的“安全”TLS 连接为真实用户提供服务。这确实是在 KLAYswap 攻击中发生的事情，并且使该攻击对于互联网上的其他安全应用程序来说尤其可怕。攻击者劫持了developers.kakao.com，接近了证书颁发机构ZeroSSL，为developers.kakao.com请求了一个证书，并将该证书提供给通过可能是“安全”TLS下载javascript库的KLAYswap用户。

虽然普林斯顿大学的研究人员预见到了这种攻击并有效地部署了针对它的第一个对策，但全面保护网络免受攻击仍然是一项持续的工作。

自从我们在 HotPETS'17 现场演示此类攻击以及我们的 USENIX Security '18 论文“Bamboozling Certificate Authorities with BGP”中提出针对 PKI 的 BGP 攻击分类法以来，我们一直在积极致力于开发针对它的防御措施。最有效的防御手段（我们小组在 2018 年 USENIX 安全论文中提出的）被称为多据点域控制验证。

在多据点验证中，CA从分布在互联网上的许多据点而不是容易受到BGP攻击影响的单一据点进行域控制验证。正如我们在2021年USENIX安全论文中所衡量的，这很有效，因为许多BGP攻击只局限于互联网的一部分，所以对手劫持一个CA的所有不同据点的可能性会大大降低（与传统的域控制验证相比）。我们与世界上最大的网络PKI CA Let's Encrypt合作，全面部署了多据点验证，他们签署的每份证书都是使用这项技术验证的（自2020年2月部署以来已超过10亿份）。Cloudflare也同样开发了一个部署，可供其他感兴趣的CA使用。

但是仅在单个 CA 上进行多据点验证仍然不够。 互联网的健壮程度取决于其最薄弱的环节。目前，Let's Encrypt 是唯一使用多角度验证的证书颁发机构，对于许多域，攻击者可以选择在攻击中使用哪个 CA。为防止这种情况发生，我们提倡通过 CA/浏览器论坛（CA 的管理机构）进行普遍采用。

此外，一些 BGP 攻击仍然可以欺骗 CA 的所有据点。 为了减少 BGP 攻击的影响，我们还需要对路由基础设施进行安全改进。在短期内，资源公钥基础设施 (RPKI) 等已部署的路由技术可以显着限制 BGP 攻击的传播，并大大降低其成功的可能性。 如今，RPKI 仅覆盖全球路由表的 35%，但随着越来越多的网络采用这项新技术，这一比例正在迅速增长。 从长远来看，我们需要一个更安全的互联网底层路由层。 这方面的例子有 BGPsec——其路由器以加密方式签署和验证 BGP 更新消息（尽管当前的路由器硬件无法足够快地执行加密操作）和像 SCION 这样的全新计划，它改变 IP 数据包的格式以提供更安全的数据包转发和路由决策。

总体而言，看到攻击者在现实世界中执行这种攻击让我们意识到保护 PKI 免受路由攻击具有非常重要的意义。如果我们想继续安全地使用信任 Web 的应用程序，则必须继续使用 RPKI 和多据点域验证。 与此同时，数以千计使用 TLS 来抵御网络攻击的应用程序很容易受到攻击，就像 KLAYswap 一样。
