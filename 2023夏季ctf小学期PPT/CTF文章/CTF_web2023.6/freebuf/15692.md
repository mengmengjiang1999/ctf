暴力破解简述

**暴力猜解简单来说就是不停的发送有可能的账号，密码组合，直到登录成功为止。

暴力破解形式

信息明确情况下

可以先确定账号（用于获取多个账号，在明确账号存在的情况下），再破解密码，如下图。

信息不明确情况下

可以指定账号，猜测密码（攻击者知道某个账号存在。如admin，张三，虽然提示用户名/密码错误，但是攻击者怀疑admin用户存在）

可以指定密码，测试账号（攻击者不知道哪些账户存在，但是怀疑系统中有弱口令，如123456/111111/888888等）

暴力猜解的整改建议

一般我们会建议用户添加验证码机制。

ps。查看有些防暴力猜解会有增加密码复杂度的建议。个人认为有很大的程度降低了暴力猜解的成功率。但是暴力猜解还是暴力猜解（还是能猜）。和这个问题的解决关系不大。

客户答疑

1.我们有锁用户这个机制（密码错误5次用户锁定）。不存在这个问题！

答：我们目前解决的是暴力破解的问题。和用户锁定关系不大。很多时候攻击者用户名和密码2个要素都不确定。攻击者通过123456这样 的弱口令搭配猜账户的行为进行系统登录，所以密码错误N次锁用户并没有对暴力猜解进行有效的防护。

2.之前按照你这边的整改建议已经加添验证码了，复测这个问题怎么还有？

答：验证码在一次验证后未失效，可以反复使用。验证码机制未起作用.如下图

/**
 * Servlet implementation class ImageServlet
 */
@WebServlet("/ImageServlet")
public class ImageServlet extends HttpServlet {
	private static final long serialVersionUID = 1L;

    /**
     * @see HttpServlet#HttpServlet()
     */
    public ImageServlet() {
        super();
        // TODO Auto-generated constructor stub
    }

	/**
	 * @see HttpServlet#doGet(HttpServletRequest request, HttpServletResponse response)
	 */
	protected void doGet(HttpServletRequest request, HttpServletResponse response) throws ServletException, IOException {
		//定义一个图片缓存BufferedImage用以暂存图片，设置高、宽
		BufferedImage  bi = new BufferedImage(68, 22, BufferedImage.TYPE_INT_RGB);
		//从图片缓存中得到一个图g
		Graphics g = bi.getGraphics();
		//定义一个颜色c
		Color c = new Color(202,147,255);
		//将g的颜色设为c
		g.setColor(c);
		//将图g填充进指定的矩形。fillRect
		g.fillRect(0, 0, 68, 22);
		//将所有字母和输入存入一个字符数组。toCharArray：Converts this string to a new character array
		char[] ch = "ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789".toCharArray();
		//从字符数组中随机获取四个字符
		//首先生成随机数
		Random r = new Random();
		//获取字符数组的长度
		int len = ch.length,index;
		//定义一个StringBuffer来缓存字符
		StringBuffer sb = new StringBuffer();
		//循环4次随机获取四个字符
		for (int i = 0; i < 4; i++) {
			//nexyInt(n) 返回一个大于0小于n的随机整数，即ch中随机的下标
			index = r.nextInt(len);
			//给g一个随机的颜色
			g.setColor(new Color(r.nextInt(88),r.nextInt(188),r.nextInt(255)));
			//将字符画入g中
			g.drawString(ch[index]+"", (i*15)+3, 18);
			//将字符组合起来存入sb
			sb.append(ch[index]);
		}
		//将sb转换成字符串，存入session
		request.getSession().setAttribute("piccode", sb.toString());
		//将bi以jpg格式写出
		ImageIO.write(bi, "JPG", response.getOutputStream());
	}
}

项目结构

逻辑讲解

用户打开index.jsp 系统通过 表情发起请求，如下

<img alt="验证码" id="imagecode" src="<%=request.getContextPath() %>/ImageServlet" />


向ImageServlet发起了一个请求，生成一张验证码图片，并且把生成的验证码放入了session中，如下

request.getSession().setAttribute("piccode", sb.toString());


用户点击提交按钮，系统将用户提交的和session中存在的进行比对，一致则验证码正确。不一致就是错误

if(checkcode.equals(piccode))


问题

用户验证验证码通过后，原来的验证码并没有失效，在session中还是原来的那个，所以这份代码并没有有效的阻止暴力猜解这个问题。虽然加了验证码，但是对于安全工作者来说，等同于没加。

我们可以输入一个正确的验证码，然后一直利用这个验证码进行破解

ps.这个请求如同使用burp等截包工具，用户没有重新加载index.html。验证码一直没有被刷新。有的程序也单独验证验证码，通过后验证码登陆请求，这里不做讨论。

解决

我遇到的大多数问题的关键在于验证码验证一次后，没有刷新。

我想把用户分成两种，一种是正常用户，一种是安全测试工作者

正常用户我觉得一定会到用户界面（index.jsp）进行操作。这样就保证可每次访问index.jsp都会发起生成验证码的请求，session中的验证码会重新加载。这是一个正常的逻辑。

安全测试会得到一个正确的验证码后无限的重发请求，仅变更请求中的部分查询值。这就需要验证一次后把验证码设置null或者重新调用一下ImageServlet刷新session中的值。这样会把安全测试导入到和用户一个登陆逻辑。

在LoginServlet.java中out.println("验证码输入正确");后面加入如下代码：

request.getSession().setAttribute("piccode", null);


当验证码成功后，将验证码设置为null。没有任何值能匹配上。只有重新执行ImageServlet（jsp页面刷新走js请求后台），重新在sesssion中放入一个值。
