安全运营之SOAR：添砖加瓦
2021-02-18 15:04:02

SOAR目标

SOAR旨在将日志中心收集到的数据、安全事件案例、标准化工作流和人工分析相结合，使组织能够实施复杂的纵深防御能力，从而使安全运营效率更高，更进一步帮助安全团队将无穷无尽的安全告警迅速收敛形成有效的安全事件、尽可能的自动化处理安全事件。

那么，要实现SOAR目标功能，我们应该如何建设SOAR呢？我们认为一个良好的SOAR平台至少要解决以下问题：

1、SOAR能操作调度每个独立的平台的功能。我们需要让SOAR对接每个独立的平台接口，将需要的功能整合封装后通过API的方式提供给PlayBook使用。

2、收集每个独立的平台安全事件/安全告警。我们需要搭建一个日志中心，须支持主动采集或被动接收每个独立平台的日志信息、告警信息等。

3、SOAR产生的事件，能方便的查看安全事件的过程信息、多个独立安全平台事件的关联信息。通过灵活的任务编排流程，快速得到一个目标结果。我们需要一个SOAR引擎，执行PlayBook关联信息。

前篇已经介绍了第三点的实践经验，接下来，将分享如何实践解决第一、第二点。

API接口模块选型

选择适合团队的API接口模块非常重要，API接口模块就像是SOAR平台的支柱，支撑着SOAR引擎上所有PlayBook的调用。由于团队的技术栈以python为主，所以在选型API接口模块我们仅考虑以python来开发RESTful API。python的web框架主流的大部分实践基于flask、tornado等，最终我们选择当下较火的FastAPI。

选择FastAPI的理由主要是性能相对较好，同时FastAPI整合了Swagger，让团队开发更加敏捷，可以让我们更聚焦于SOAR的接口建设，不需要考虑使用yapi等更庞大的接口管理平台。

API样例

通常我们将SOAR提供的单个产品的接口集合称为一个应用，在部署API应用时，我们可以有选择的给与请求大的应用更多的资源（cpu、内存、甚至更多的实例等）。

接口设计环节，需要关注两点，接口参数以及接口描述。一个清晰的接口描述非常重要，每个接口的开发由团队完成，接口的功能以及作用描述不清晰的话，会导致PlayBook开发困难，很可能陷入不断在调试如何调用接口，调试如何处理返回结果的深渊之中。

选型FastAPI作为API开发框架，很重要的原因之一是整合Pydantic（强制做类型检查的模块），可以让我们快速解决接口参数验证问题。

下面将挑选SOAR平台对接腾讯云安全组的添加入站规则接口分享经验。

数据验证&接口描述

在对安全组的规则操作过程中，需要对规则的优先级、IP/网段、协议、端口等字段做数据验证，避免产生生产级风险。Pydantic很好的帮助我们实现这点，可以看到，规则内容主要在SecurityGroupPolicySet中的对象SecurityGroupPolicyIngressSet中进行设置与验证。

每个字段都需要尽可能的描述清楚含义以及取值范围，便于开发playbook的同学能快速的上手。对于设置取值范围的字段，不仅仅是描述上有要求，还需要在接口调用时做数据验证。

如对动作类型Action我们要求必须是ACCEPT或DROP

日志中心

日志中心目前最好的（不花钱的）选型当然是大家耳熟能详的elk，这里不详细介绍elk如何部署与搭建，这方面的文章很多，这里主要介绍一下日志中心在实践过程中的一些心得。

采集安全日志的重点主要是两方面，一方面是日志存储要满足安全合规要求以及业务要求、另一方面是日志字段范式化，对不同来源的日志要提前做好规划，未来将如何使用。

冷热架构

配置elk索引的ILM（索引生命周期策略），实现索引定期合并segments并从热节点转移至温/冷节点，当数据过期后，自动删除。如下图，建议将主分片及segments设置合并为1。

冷热架构使得elk在检索热数据时极大地提升检索速度，如果你在查询数据时经常出现检索超时，可能需要往这方面去考虑改进。

合适的模板（Template）

设置合适的索引模板，重点在于设计规范索引的分片数，刷新数据时间以及日志字段分词类型，同样能够降低elk的负载以及提升检索效率。

下面举例最常见的防火墙日志模板设置（字段内容节选部分举例）

PUT _template/fw_xxx_ilm_tepl
{
  "index_patterns": [
    "sp_fw_xxx_*"
  ],
  "settings": {
    "index": {
      "routing.allocation.require.box_type": "hot",
      "number_of_shards": 5,
      "number_of_replicas": 0,
      "refresh_interval": "60s"
    },
    "analysis": {
      "analyzer": {
        "standard_lowercase": {
          "type": "custom",
          "tokenizer": "standard",
          "filter": [
            "lowercase"
          ]
        }
      }
    }
  },
  "mappings": {
    "doc": {
      "properties": {
        "action": {
          "type": "text",
          "analyzer": "standard_lowercase",
          "fields": {
            "keyword": {
              "type": "keyword"
            }
          }
        },
        "create_at": {
          "type": "date",
          "format": "yyyy-MM-dd HH:mm:ss||epoch_millis"
        },
        "dest_ip": {
          "type": "ip",
          "fields": {
            "keyword": {
              "type": "keyword"
            }
          }
        },
        "rule_name": {
          "type": "text",
          "analyzer": "whitespace",
          "fields": {
            "keyword": {
              "type": "keyword"
            }
          }
        },
        "src_ip": {
          "type": "ip",
          "fields": {
            "keyword": {
              "type": "keyword"
            }
          }

      }
    }
  }
}

防火墙日志最大的问题是量大，在安全运营过程中经常出现的排查问题时检索日志信息超时，在关键的时候不能快速检索定位，那这块日志收与没收有什么区别呢？

我们预设防火墙索引模板，设置5分片并且放在热节点，数据落盘刷新时间refresh_interval设置为60s，通过牺牲数据准实时性，降低磁盘io压力（如果磁盘io压力不大，可以缩小refresh_interval时间）。对字段设置需要使用的分词类型，降低每个字段所占用的空间，便于防火墙日志的存储。

冷热架构以及合理的设置索引配置，使得我们防火墙日志集群存储近百亿数据也能快速的检索相关日志信息。

结尾

我们使用SOAR聚焦于提升安全运营效率，释放人力，将平时运营工作转换成代码，最终实现半自动化甚至全自动化。后续将分享实践过程中如何通过playbook提升我们的运营效率，如自动化处理防火墙/vpn工单、某些类型漏洞自动化闭环等。
