动态链接介绍

之前所说的静态链接有诸多优化的地方（但并不意味着静态链接无人使用，在某些情况下还是要使用静态链接的）比如说：

过分浪费磁盘与内存的空间

无法进行动态的更新

为了解决上述的问题，使用动态链接。

动态链接要解决的问题

所有动态链接，就是将链接的过程推迟到运行时进行

静态链接得到的可执行程序，被操作系统加载后便可执行，因为如上篇文章所述，在链接的时候就已经将所有目标文件中的代码、数据等Section合并到可执行文件中了。在这个过程中还会将目标文件中所使用的外部符号（变量、函数等）全部进行了重定位，指向了其在虚拟地址中的位置，所以可执行程序执行的时候无需依赖外部模块就可运行（所需要的”外部模块”都已经合并到可执行文件中了），总结一下：对于静态链接，在链接阶段，符号重定位过程中会直接对可执行文件中需要重定位的符号进行修改完成重定位。

但这种事情到了动态链接就不那么容易完成了，由于动态链接要将链接的过程推迟到运行时，也就是说运行过程中：当前可执行文件与所依赖的动态链接库被加载进内存后，调用可执行程序的入口函数前，才会对可执行文件中引用的外部符号进行重定位（也就是将这些符号在动态链接库中的虚拟地址填到对应调用的位置）

此时就会产生一个很关键的问题：

代码段是不可写的！！

原因就不用解释了，若代码段可写将毫无安全性可言，而且会扰乱代码的执行逻辑（早期出现过代码段可写的机制）

所以想像静态重定位那样，直接修改代码中对应调用外部函数/变量的位置的地址是绝对不可能的！

所以如何解决这个问题，就是动态链接的核心

动态链接的核心

Butler Lampson 曾说过这样一句话：

Every problem in computer science can be solved by adding another level of indirection

计算机科学中的所有问题都可以通过增加另一层来间接解决

虽然代码段在加载后是不可写的，但哪个地方是可写的呢？

数据段！

虽然无法直接改写代码段中外部变量/函数的实际地址，但我们可以将外部变量/函数的实际地址放到数据段的某个位置中，让代码段先引用数据段中的内容，重定位时直接修改这个数据段中保存的地址到外部变量/函数的虚拟地址即可完成重定位，就完成了动态链接

而这个思路就是实现动态链接的最优思路，他有另一个名称：

地址无关代码（PIC, Position-independent Code）也就是 GCC 会默认加上的选项-fPIC

此时使用到的共享库在虚拟内存中仅存一份，若使用到了共享库中的数据则会复制到各自的进程中

但这种思路会有安全问题的产生：既然数据段存放了可执行文件中要执行函数重定位后的实际虚拟地址，数据段又有 写 权限，这就意味着通过一些手段（比如说溢出）我们也可以覆盖其地址达到定位到其他函数的目的，比如若可执行文件本身调用了一个libc中的函数，通过修改这个地址，就有可能定位并使用libc中的另一个函数 system 达到出弹shell的目的

另一种实现动态链接的方式

地址无关代码无疑是最优的动态链接解决方案，但若只使用-shared选项 而没有开启-fPIC则使用了另一种动态链接的方式：装载时重定位

共享对象也就是动态链接库在被装载到物理内存后，始终是只有一份的，不管有多少个进程使用它。但是对于每一个进程，共享对象会映射一次到虚拟地址空间，也就是每个进程空间都有一份共享对象的映射，但是，对于不同的进程，映射的地址（基址）是不一样的（大部分情况下），所以在装载时将动态链接库映射到每一个进程中时，是需要根据该进程空间的地址修改物理内存中动态库中的指令中的地址（比如说跳转指令或是变量的访问等）

所以这就产生了缺点：没有办法做到同一份指令被多个进程共享

一些可能会用到的函数

  * dlopen()

dlopen()

用于打开一个共享对象（动态库）将其加载进进程空间中，完成初始化

void *dlopen(const char *filename, int flags);

  * const char *filename要打开动态库的路径

    If filename is NULL, then the returned handle is for the main program.

    若文件名为空，返回该进程的全局符号表

    如果filename是0,那么dlopen会返回全局符号表的句柄，我们可以在运行时找到全局符号表里的任何符号，并可执行他们。全局符号表包含了程序的可执行文件本身，被动态链接器加载到进程中的所有共享模块已经在运行时通过dlopen打开并使用RTLD_GLOBAL方式的模块中的符号。

  * const char *filename函数符号的解析方式

      + RTLD_LAZY延迟绑定（具体内容会在后面说，现在简单说一下）

        当函数第一次被用到时才由动态链接器进行绑定（符号查找，重定位等），没用到的不绑定。这提高了程序的启动速度

      + RTLD_NOW当模块被加载时完成所有的函数绑定工作，如果有任何未定义的符号引用的绑定工作没法完成，那么dlopen()就返回错误

    上述选项 二选一

RETURN VALUE

最终返回值返回一个动态库的指针

On success,dlopen()return a non-NULL handle for the loaded object. On error (file could not be found, was not readable, had the wrong format, or caused errors during loading), these functions return NULL

dlsym()

使用该函数从通过dlopen()打开动态库获得的句柄（handle）中找到指定的符号

void *dlsym(void *handle, const char *symbol);

  * void *handle动态库句柄
  * const char *symbol要查找符号

RETURN VALUEOn success, these functions return the address associated with symbol. On failure, they return NULL; the cause of the error can be diagnosed using dlerror(3).

成功返回查找符号的地址，失败返回NULL

dlerror()

判断上一次调用是否成功

char *dlerror(void);

每次调用dlopen()、dlsym()或dlclose()以后，都可以调用dlerror()函数来判断上一次调用是否成功。dlerror()的返回值类型是char*，如果返回NULL，则表示上一次调用成功；如果不是，则返回相应的错误消息

dlclose()

关闭一个动态库，将一个已经加载的模块卸载

int dlclose(void *handle);

1：动态库的自举

动态链接器负责在执行程序时对其依赖的对动态库进行加载

在执行main时，操作系统会首先将main加载到内存中，然后根据.interp段的信息来获得动态链接器的路径

.interp段的内容很简单，其中保存了一个字符串，这个字符串就是可执行文件所需要的动态链接器的路径

通过objdump查看该段的内容

objdump -s main

可以获得动态链接器的路径为/lib/ld-linux.so.2

可以看到动态链接器本身也是一个动态链接库（共享对象Glibc的一部分），但特殊的地方在于动态链接器不依赖于任何动态库，否则当他加载的时候没有人为他来加载，并且动态链接器本身所要的全局和静态变量的重定位工作必须由它本身完成，所以这项自我重定位的代码必须在动态链接器启动时来完成，这个过程往往被称为 自举（Bootstrap），所以动态链接库的入口地址就是自举代码的开始处

动态链接器本身是静态链接的

  * 所以执行main时，会首先将 动态链接器 映射到main进程的虚拟地址空间中

    下面这段话在全文看完后回看会更容易理解

    此时动态链接器会先执行自举代码：首先定位自己的GOT表，GOT表中的第一个入口就是.dynamic短偏移地址，通过该段中的信息自举代码便可以获得动态链接器本身的重定位表和符号表等，从而得到动态链接器本身的重定位入口，先将它们全部重定位。从这一步开始，动态链接器代码中才可以开始使用自己的全局变量和静态变量

  * 完成基本自举后，动态链接器将main和 链接器本身的符号表合并到一个符号表中，也就是 全局符号表

  * 随后链接器便开始寻找可执行文件所依赖的共享对象，在.dynamic段中有一种入口为DT_NEEDED指出是当前可执行文件所依赖的共享对象

  * 由此，链接器可以列出main所需要的所有共享对象，并将这些共享对象的名字放入到一个装载集合中

      + liba.so
      + libc.so.6

  * 然后链接器开始从集合里取一个所需要的共享对象的名字，找到相应的文件后打开该文件，读取相应的ELF文件头和.dynamic段，然后将它相应的代码段和数据段映射到进程空间中

  * 如果这个ELF共享对象还依赖于其他共享对象，那么将所依赖的共享对象的名字放到装载集合中。如此循环直到所有依赖的共享对象都被装载进来为止

      + libb.so(liba.so依赖 )

执行main后有两种方式可以观察其虚拟地址空间

cat /proc/PID/maps

pmmp PID

全局符号表 与 .dynamic 表

在静态链接的过程中，链接器在第一遍扫描的时候会将每一个目标文件中的符号提取出来生成全局符号表，并在第二次扫描的时候查看每个目标文件中需要重定位的符号，在全局符号表中确认其位置并把这个地址填到引用的地方

而由于动态链接的特性，所以每个符号在运行时才能知道其具体地址，所以这个生成全局符号表的责任交给了动态链接器

而我们main进程的功能就是通过dlopen于dlsym打印输出main进程全局符号表中相关符号的地址信息，先来看其执行结果

可以看到定义的s开头（静态变量）的无论是变量还是函数在main的全局符号表中都找不到其地址，而其他的都正常，这是为什么？

在回答这个问题之前先说两个表.dynamic和.symtab

.symtab并不陌生，就是符号表，也就是模块中的所有符号

.dynamic就是所说的动态符号表，动态符号表中记录着模块中符号的导出和导入关系，是.symtab的一个子集

所以对于一个动态链接库，只有在动态符号表中的符号才会被导出，而由于static类型的特性，所以被其修饰的符号并不会放到动态链接表中，这也就解释了为什么在main的全局符号表中找不到liba.so和libb.so中的static符号

2：重定位与初始化

执行完以上过程后，链接器会再次重新遍历可执行文件和每个共享对象的重定位表（.rel.），将它们的GOT/PLT中的每个需要重定位的位置进行修正

由于liba.so具有更多的依赖与被依赖关系，所以接下来对关键的几个表的观察以liba.so为例

重定位表 .rel.

动态链接中会通过两个重定位表来告诉链接器哪些符号需要重定位：

  * .rel.dyn对数据引用的修正（它所修正的位置位于GOT表（.got）中以及数据段）
  * .rel.plt对函数引用的修正（它所修正的位置位于GOT表（.got.plt））

通过指令readef -r liba.so来观察重定位表

其中对于重定位入口的类型有两种分别为：

  * R_386_GLOB_DAT
  * R_386_JUMP_SLOT

这两种类型表示被修正的位置只需要直接填入GOT表中的地址即可

全局偏移表 GOT

前面说过在执行程序过程中执行重定位会通过增加一个中间层来实现运行时重定位的功能，那么这个中间层就由 全局偏移表GOT来实现：比如说如上所示liba.so中会引用libb.so中的全局变量g_nVarB,所以在liba.so代码段中，会将引用g_nVarB的位置处g_nVarB的地址改为GOT表的地址（GOT对应表项的地址），这样只需在重定位时将其地址放入位于数据段的GOT表中即可

动态链接库中的 GOT 表

动态链接库中存在两个GOT表：

  * 重定位变量符号.got
  * 重定位函数符号.got.plt

从图中可以看到.got与.got.plt的大小均为24字节，说明每个里面都有6个表项（每个表现占 4 字节）

且可以从Off一项看到：

  * .got距离文件头的偏移为0x002fe8
  * .got.plt距离文件头的偏移位0x003000

再从加载器的角度来看看.got表 与.got.plt表的位置又在哪里捏？

还要注意一个点，可以看出第一个段起始的VirtAddr（虚拟地址）为0x00000000，这是因为开启了位置无关代码参数（-fPIC），当liba.so的代码段和数据段被加载进内存时，动态链接器会随即找到一块空闲空间，将这块空间的起始地址作为liba.so的虚拟起始基地址，然后以VirtAddr作为其偏移地址即可

可以看到其第4个LOAD段的起始地址正是0x003ef8也就是.init_array的虚拟地址（非最终的虚拟地址，最终的虚拟地址需要在运行时加上基地址）

而根据Section Headers中可以算出，.init_array与.got之间的偏移为0x2fe8 - 0x2ef8 = 0xf0

再用0xf0 + 0x003ef8=0x3fe8这也就是.got的起始地址

0x3ef8 + 18 = 0x4000这也就是.plt.got的起始地址

当然这算来算去起始并没有什么意思，直接从Section headers中就可以获取该Addr

重定位表与GOT表的关系

细心可能会发现重定位表中要重定位符号的偏移地址正好与.got和.plt.got表中的表项重合，这也正验证了一开始所说的，因为动态链接中将要重定位的符号的地址都指向了GOT表某条表项，所以动态链接器只需要对GOT表中对应偏移的表项进行重定位

其中 GOT 表的前三项为三个公共表项，这三个表项的作用分别为：

 1. got[0]本ELF动态段(.dynamic段)的装载地址
 2. got[1]本ELF的link_map数据结构描述符地址（本模块的ID）
 3. got[2]_dl_runtime_resolve函数的地址

<__x86.get_pc_thunk.bx> 的作用

用于获取调用该函数的函数体中，下一条指令的地址

由于调用该函数的函数在call 1080 <__x86.get_pc_thunk.bx>时，会将下一条指令的地址入栈用于返回，所以该指令直接将栈顶指针esp所指向的这个地址保存在ebx中

⚠️ 注意：只有32位环境下会这么来获取下一条指令的地址，因为32位环境下是不支持直接访问eip寄存器的，64位环境下就可以了

首先来看11da处的两行代码

1128:       e8 53 ff ff ff          call   1080 <__x86.get_pc_thunk.bx>
112d:       81 c3 d3 2e 00 00       add    ebx,0x2ed3

  * call 1080 <__x86.get_pc_thunk.bx>将112d放入ebx中
  * add ebx,0x2ed3ebx = ebx + 0x2ed3 = 0x112d + 0x2ed3 = 0x4000

这个0x4000也就是.plt.got的偏移地址

⚠️ 在实际程序执行加载该动态库时，通过call获得的就是虚拟地址，通过+ 0x2ed3这个偏移，就可以成功算出实际.plt.got的虚拟地址

可以看到之后的对于重定位表中变量的操作都是借助ebx来进行（位处于重定位表中的变量在确认其偏移位置时也会借助ebx的值，因为.data段就在.got.plt之后）

但函数的调用却借用了一个另外的Section.plt

关于.plt就要提到另外一个功能 延迟绑定（PLT)

延迟绑定（PLT）

由于动态链接下对于全局数据的访问和跨模块的调用都要进行复杂的GOT定位，然后间接寻址或调用，导致程序的运行速度减慢大概1%~%5。又因为动态链接的链接工作在运行时完成，导致程序的启动速度减慢。

程序运行过程中，会有很多函数没有用到（错误处理函数，没有使用的功能模块等），所以没有必要一开始就把所有函数都链接好，ELF采用延迟绑定的方法，基本思想是当函数第一次被用到时才由动态链接器进行绑定（符号查找，重定位等），没用到的不绑定。这提高了程序的启动速度

如何实现 延迟绑定

ELF通过PLT（Procedure Linking Table） 来实现延迟绑定

在Glibc中，动态链接器完成绑定工作的函数叫_dl_runtime_resolve()，它必须知道绑定发生在哪个模块中的哪个函数，因此假设其函数原型为_dl_runtime_resolve(module, function)当调用某个外部模块的函数时，并不直接通过GOT跳转，而是通过一个叫作PLT项的结构来进行跳转，每个外部函数在PLT中都有一个相应的项

<fnA3@plt>为例

001050 <fnA3@plt>:
    1050:       ff a3 10 00 00 00       jmp    DWORD PTR [ebx+0x10]
    1056:       68 08 00 00 00          push   0x8
    105b:       e9 d0 ff ff ff          jmp    1030 <_init+0x30>


为了实现延迟绑定，链接器在初始化阶段并没有将fnA3()的地址填入到[ebx+0x10]对应的GOT表项中，而是将push 0x8的地址填入到[ebx+0x10]对应的GOT表项中，这个步骤不需要查找任何符号，所以代价很低。很明显，第一条指令的效果是跳转到第二条指令，相当于没有进行任何操作

第二条指令push 0x8将一个0x8压入堆栈中，这个数字是fnA3这个符号引用在重定位表.rel.plt中的下标

然后jmp 1030 <_init+0x30>跳转到_dl_runtime_resolve这实际上就是在实现_dl_runtime_resolve函数调用，它在进行一系列符号解析和重定位工作以后将fnA3()的真正地址填入到[ebx+0x10]对应的GOT表项中

之后当我们再次调用<fnA3@plt>时，第一条jmp指令就能够跳转到真正的fnA3()函数中
