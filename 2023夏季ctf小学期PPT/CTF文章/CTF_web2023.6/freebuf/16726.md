Log4j2漏洞原理性分析
2021-12-13 11:32:35

本地撸的项目由于未知原因无复现漏洞所以参考了这个git 项目，链接如下：

https://hub.fastgit.org/christophetd/log4shell-vulnerable-app

*hub.fastgit.org这个域名为github的国内镜像地址，大家也可以使用 www.github.com进行访问

启动项目执行payload

curl 127.0.0.1:8080 -H 'X-Api-Version: ${jndi:ldap://127.0.0.1/a}’

此处仅提供安全学习使用所以不使用真实payload进行展开，仅研究此处漏洞发生逻辑

所用的log4J2版本为 2.14.1

由于127.0.0.1/a 并无真实资源因此会抛出异常

Error looking up JNDI resource [ldap://127.0.0.1/a]. javax.naming.CommunicationException: 127.0.0.1:389 [Root exception is java.net.ConnectException: Connection refused (Connection refused)]

上图为异常发生时所输出的堆栈信息，漏洞之谜包含其中

调试

根据堆栈信息一路调试，直到

StrSubstitutor.substitute(final LogEvent event, final StringBuilder buf, final int offset, final int length, List<String> priorVariables)

该函数发现开始有针对日志输出的message内容进行解析的行为

由此发现该函数会默认针对包含 ${ 的数据进行特殊处理

该函数整体的调试过程这里省略（由于逻辑较为复杂可能占太大篇幅影响正常分析观看）

结论：

1.默认情况下，在输入日志中存在，${ 且存在 } 闭合的数据内容时，取出其中的内容往后续的函数resolveVariable传输

2.当存在多对 ${${XXX1} ${XXX2} …XXXn}会遍历所包含的日志逻辑所包含的全部的n个内容 n 次。

3. 存在 { 但是不满足 全部都与}成对闭合的情况下不会进入 resolveVariable 进一步处理

下面是关于resolveVariable 的分析 代码很简单 核心就是调用StrLookup 进行lookup

先进入Interpolator 的lookup函数中，程序将会根据前缀分配lookup实例

可被解析的前缀有如下列表，此处指向JNDI

在JndiLookup对象的 lookup函数中

jndi:ldap://127.0.0.1/a

上述的地址被成功解析并通过JndiManager进行实质处理

后续的攻击手法可参考

https://hub.fastgit.org/mbechler/marshalsec结合JNDI注入外部对象并执行

漏洞的整个原理一句话概括就是,默认使用log4j2 时，它会解析并记录日志内容同时支持了JNDI语法导致了该问题。

相比于常见的web攻击手法，由于记录日志的场景很多很复杂，针对日志内容的注入防范难度可能更高，除去直接通过请求构造payload 甚至可以通过一些正常的文件上传来间接实现注入。

当然这个漏洞之所以是核弹还是因为log4j2 普及率太高，而这个漏洞的利用难度也很低，由于log4j2拆包即用的特性即使进行相关配置补充也很难意识到需要限制msglookup功能。

https://www.freebuf.com/articles/web/308238.html

这里最后介绍了一部分解决方案引用一下

1）添加jvm启动参数-Dlog4j2.formatMsgNoLookups=true；

2）在应用classpath下添加log4j2.component.properties配置文件，文件内容为log4j2.formatMsgNoLookups=true；

3）JDK使用11.0.1、8u191、7u201、6u211及以上的高版本；

4）部署使用第三方防火墙产品进行安全防护。
