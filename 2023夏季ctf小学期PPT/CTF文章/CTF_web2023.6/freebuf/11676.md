2 协议相关

在BlueBore（CVE-2017-0785）中讲了L2CAP的分段机制，这次用到的是分片

先区分一下

分段重组（Segmentation and reassembly, SAR)

上层应用数据（SDUs）的分割和重组，生成协议数据单元，以满足用户数据传输对延时的要求，并便于后续的重传、流控等机制的实现

分片重组(Fragmentation and Recombination)

协议数据单元（PDUs）的分片和重组，生成符合Link Layer传输要求的数据片，长度不超过251


2.1 HCI数据包格式

HCI有数据、命令和事件三种类型的包

命令包COMMAND（0x01）只能从主机发往主机控制器

数据包是双向的，分为两类：ACL（0x02）、SCO（0x03）

事件包EVENT（0x04）始终是主机控制器发向主机的

由于漏洞发生在ACL链路层，这里只分析ACL数据包格式

其中，Handle我们要在执行poc时动态获取

PB FLAGS == 00(bit) 时，代表 Host -> Contoller 的 L2CAP 的首包

PB FLAGS == 10(bit) 时，代表 Contoller -> Host 的 L2CAP 的首包

PB FLAGS == 01(bit) 时，代表 Host -> Contoller 或者 Contoller -> Host 的 L2CAP 的续包

2.3 分片重组

L2CAP作为ACL包通过与HCI相同的UART连接发送

它需要按照最大ACL数据包长度进行分割

在主机上的驱动程序进行固件初始化期间，HCI命令读取缓冲区大小

如果接收到的L2CAP数据包的长度大于缓冲区的最大长度，这个数据包就会被分片重组

部分包保存在名为 partial_packets 的map中，使用

连接句柄作为key

接着分配一个足够大的缓冲区来容纳最后的数据包，然后把接收到的数据复制到该缓冲区

最后接收到的分片的结尾保存在 partial_packet->offset 中


我们可以简单把 L2CAP 当成 HCI data payload

4攻击思路

在发生截断时

packet->len = partial_packet->len – partial_packet->offset

= 重组结果的预期完整长度（含HCI-ACL头）- 重组结果已有有效数据的长度（含HCI-ACL头）

前文中的 packet->len 是包含HCI-ACL头的

而此时的 packet->len 不包含HCI-ACL头

接着，源码又用 packet->len - packet->offset

此前已经设置 packet->offset = HCI_ACL_PRESMBLE_SIXE

所以此处多减去了一个4

而我们只需要控制续包中 packet->len 小于 4，例如2

那么 packet->len - packet->offset == -2

且memcpy时，强转为无符号数，即0xfffffffffffffffe

就产生了溢出

在漏洞修复代码中，也可以看到，计算packet->len时，又加上了一个packet->offset


5构造

按照我们分析的分片格式，分别构造首包和续包

首先，构造首包时

使得 L2CAP 头中的Length为 Command 请求体第1部分长度 + 2

这样在解析时，就会判定，Command 请求体第2部分长度为2

然后在续包的HCI-ACL头的Length设定大于2，从而触发截断

导致memcpy时溢出
