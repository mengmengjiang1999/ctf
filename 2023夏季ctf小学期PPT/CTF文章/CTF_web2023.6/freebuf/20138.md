SQL的前置知识

SQL是一种标准，用于关系型数据库编程语言。我们知道，标准是一回事儿，具体实施又是另一回事儿。不同数据库细节上可能会出现差异性。

以下是数据库的表。

SQL 语句可用于修改数据库表及其索引结构，以及增删改查数据行。

命令分为三种类型：

数据操作语言 (DML) 数据定义语言 (DDL) 数据控制语言 (DCL)

攻击者可以使用每一种类型来破坏系统的机密性、完整性和可用性。

场景练习

让我们查一下这个人在哪个部门

Data Manipulation Language (DML) 数据操作语言

顾名思义，数据操作语言处理数据的操作。 许多最常见的 SQL 语句，包括 SELECT、INSERT、UPDATE 和 DELETE，都可以归类为 DML 语句。 DML 语句可用于请求记录 (SELECT)、添加记录 (INSERT)、删除记录 (DELETE) 和修改现有记录 (UPDATE)。

这里让是让我们修改一下这个人的部门

Data Definition Language (DDL) 数据定义语言 那么这里SQL注入的危害视角，变成了攻击数据结构了。

数据定义语言包括用于定义数据结构的命令。 DDL 命令通常用于定义数据库的模式。 模式是指数据库的整体结构或组织。 在 SQL 数据库中，包括表、索引、视图、关系、触发器等对象。

CREATE - 创建数据库对象，例如表和视图

ALTER - 改变现有数据库的结构

DROP - 从数据库中删除对象

这里让我们添加列"phone"，数据结构为varchar(20)，到employees表，来攻击表的结构模式。

官网搜一下，把语法拼凑起来。

ALTER TABLE employees ADD COLUMN phone varchar(20);


Data Control Language (DCL) 数据控制语言

数据控制语言用于在数据库中实现访问控制逻辑。 DCL 可用于撤销和授予用户对数据库对象（如表、视图和函数）的权限。

显而易见，这一次的视角又到了权限的地方了。

如果攻击者成功地将 DCL 类型的 SQL 命令“注入”到数据库中，他就可以破坏系统的机密性（使用 GRANT 命令）和可用性（使用 REVOKE 命令）。 例如，攻击者可以授予自己数据库的管理员权限或撤销真正管理员的权限。

DCL 命令用于实现对数据库对象的访问控制

GRANT - 授予用户对数据库对象的访问权限

REVOKE - 撤销之前使用 GRANT 授予的用户权限

赋予 operator 创建表的权限。

GRANT CREATE TABLE TO operator;


这里是要让我们将 grant_rights 表赋予未经授权的用户 unauthorized_user，去官网做数据关联，我们发现基于此处来构造的成功率很大

构造的payload如下所示：

GRANT ALL ON grant_rights TO unauthorized_user;


什么是 SQL 注入？

当来自客户端的未经过滤的数据（例如来自搜索字段的输入）进入应用程序本身的 SQL 解释器时，就会发生 SQL 注入。 如果应用程序未能正确清理用户输入（使用准备好的语句或类似语句）或根据特殊字符过滤输入，黑客可以操纵底层 SQL 语句以发挥他们的优势。

参数化查询

此思维旨在：解决数据和语义的分离，即从用户获取的一切皆为数据，而非语义，语法本身的特殊含义。

String query = "SELECT * FROM users WHERE last_name = ?";       # 已符号占位
PreparedStatement statement = connection.prepareStatement(query);
statement.setString(1, accountName);           # 再定义符号归属的字段
ResultSet results = statement.executeQuery();


存储过程

小心：仅当存储过程不生成动态 SQL 时 ，它才是安全的。

  * 安全的存储过程

CREATE PROCEDURE ListCustomers(@Country nvarchar(30))
AS
SELECT city, COUNT(*)
FROM customers
WHERE country LIKE @Country GROUP BY city

输入验证

当查询的参数不再可注入时，我们还需要验证输入吗？需要，防止其他类型的攻击被存于数据库中。

  * 存储型XSS

  * 信息泄露

  * 逻辑错误

  * 多阶段SQL注入（第一次存在参数化查询，将数据存于数据库，但后续又会从中读取并进一步被没有任何防御措施的查询语句执行）

输入验证与参数化查询需同时应用

  * 准备好的语句是否总是防止 SQL 注入？不是。

以下为编写好的Order by查询

"SELECT * FROM users ORDER BY " + sortColumName + ";" 


SQL语法规范如下：

orderExpression表达式可以是 selectExpression，也可以是一个函数

SELECT ...
FROM tableList
[WHERE Expression]
[ORDER BY orderExpression [, ...]]

orderExpression:
{ columnNr | columnAlias | selectExpression }   # 看这里selectExpression
    [ASC | DESC]

selectExpression:
{ Expression | COUNT(*) | {     # 看这里的函数
    COUNT | MIN | MAX | SUM | AVG | SOME | EVERY |
    VAR_POP | VAR_SAMP | STDDEV_POP | STDDEV_SAMP
} ([ALL | DISTINCT][2]] Expression) } [[AS] label]

Based on HSQLDB


攻击者可以实施这种payload进行注入

SELECT * FROM users ORDER BY (CASE WHEN (TRUE) THEN lastname ELSE firstname) 


您应该实现一个白名单来验证该sortColumName的值。 它应始终限于诸如“名字”或“姓氏”之类的内容。

  * 因此，输入验证与参数化查询的防御策略需要同时实施，而不是认为这个数据，不是直接来自于用户的输入。
