DNS 区域传送

DNS 区域

DNS被分为多个不同的区域。这些区域可区分在DNS命名空间中以不同方式管理的区域（DNS区域是DNS命名空间的一部分，由特定的组织或管理员加以管理），也就是说区域是DNS服务器的管辖范围

DNS区域与域名或单个 DNS服务器 是没有特定的关联关系的。DNS区域可包含多个子域，并且一台DNS服务器可能管理一个或多个区域，同样一个区域也可能会由多个DNS服务器来管理**

比如为了保证DNS服务器的可靠、冗余，一个域中可能存在一个主DNS服务器和多个辅助DNS服务器同时来管理

DNS名称服务器是通过区域来管理名称空间的,而并非以域为单位来管理名称空间

为什么要分区域管理

DNS区域是为了便于根据实际情况来分散DNS名称管理工作的负荷，将DNS名称空间划分为区域（zone）来进行管理

以CloudFlare提供的一个例子来说


其中虽然support.cloudflare.com、community.cloudflare.com和blog.cloudflare.com都为

cloudflare.com的子域，但若blog网站是一个健壮的网站需要单独管理而且support网站与community网站与cloudflare.com有更紧密的关联的话

就可以将blog.cloudflare.com放在一个单独的区域中进行管理，其余三个域名放在另外一个区域中进行管理，而不用将子域全部放在一起进行管理

在DNS服务器中必须先建立区域，然后再根据需要在区域中建立子域

DNS 区域传送

DNS是一项关键服务。如果区域的DNS服务器不工作且缓存信息已过期，则所有服务（Web、邮件等）都无法访问该域。因此，每个区域应该至少有两个DNS服务器

由于区域可能很大而且可能发生更改，在每台服务器上单独手动编辑区域数据，会花费大量时间，并且有很大的错误概率。这就是需要DNS区域传送的原因。

DNS 区域传送方式

一般有两种区域传送的方式

  * AXFR完全区域传送

    当一个新的DNS服务器添加到区域中并配置为从DNS服务器时，它则会执行 完全区域传送

  * IXFR增量区域传送

    在主DNS服务器上获取完整的资源记录副本；同时，为了保证数据同步，主域名服务器有更新时也会及时通知辅助域名服务器从而执行 增量区域传送

AXFR是一种跨DNS服务器复制DNS数据的机制，AXFR客户端在TCP端口53上连接到AXFR服务器，发送AXFR请求，接收带有请求的区域数据的AXFR响应，然后关闭连接**，但并不是唯一的，有 更好的DNS复制协议

DNS 区域文件

区域中的所有信息都存储在DNS区域文件中

区域文件是存储在DNS服务器中的纯文本文件，其包含区域的实际表示，并且包含区域内每个域的所有记录。

区域文件必须始终以 授权机构起始 (SOA)记录为开头，该记录包含的重要信息有区域管理员的联系信息

SOA Record

name         example.com                
record type  SOA                        
MNAME        ns.vulhub.org  区域主要名称服务器的名称
RNAME        sa.vulhub.org  管理员电子邮件地址   
SERIAL       1              SOA 记录的序列号  
REFRESH      3600                       
RETRY        600                        
EXPIRE       86400                      
TTL          3600                       


当区域文件中 SOA 记录的序列号发生更改时，会提醒辅助名称服务器，它们应当通过区域传送更新其区域文件的副本

AXFR响应可以包含一个区域的大量数据。为了节省时间，当AXFR客户端已经在磁盘上拥有区域数据时，它通常会避免发送AXFR请求以获取相同数据的其他副本。它通过检查SOA响应中的序列号与磁盘上区域中的序列号来实现这一点

AXFR 配置漏洞

AXFR本身不提供身份验证，因此任何客户端都可以向DNS服务器请求整个区域的副本，所以其需要依赖配置来预防任何人都可以向DNS请求整个区域的副本的问题，因此错误的配置或没有加以限制的配置就会导致该漏洞

为了防止此漏洞发生，应将 DNS 服务器配置为仅允许来自受信任 IP 地址的区域传送

由于该错误配置会导致，攻击者就能获得某个域的所有记录，甚至整个网络拓扑都暴露无遗，所以一般在信息收集阶段会尝试是否存在区域传送漏洞

vulhub中复现该漏洞

对应网址：Vulhub

docker-compose up -d启动docker后，当前机器将作为DNS服务器监听TCP/UDP 53端口，

当前我们就在KALI上进行复现，当前IP为172.16.12.140

在开始实验前，先来看一下vulhub提供的复现环境中当前DNS主服务器的区域数据库

注意看SOA的部分，再回看上面说的SOA的结构，是不是都对应上了（刚刚SOA结构种，所举得例子就是从这个数据库文件中取的值）

这也印证了 区域文件必须始终以 授权机构起始 (SOA)记录 为开头

向正常的 DNS 服务器发送请求

正常请求

dig vulhub.org @8.8.8.8

区域传送请求

dig vulhub.org axfr @8.8.8.8

可以看到正常情况下，由于我们的身份未认证，所以会直接拒绝区域传送

向存在区域传送漏洞的 DNS 服务器发送请求

正常请求

dig vulhub.org @172.16.12.140

区域传送请求

dig vulhub.org axfr @172.16.12.140

可以看到此时请求到了刚刚区域文件中的所有信息，获得了vulhub.org的所有子域名记录
